Скиллы

Что установлено, из чего состоит и как читается. Всё — из файлов на диске.

Что такое скилл

Скилл — это папка с инструкцией. Файл SKILL.md плюс справочники, которые подгружаются по мере надобности.

skills/
  mobile-reports/
    SKILL.md                    ← главный файл, читается всегда
    references/
      mobile-long-reads.md      ← подгружается по теме
      design.md
      reports.md

Когда приходит задача, я читаю SKILL.md и открываю нужный справочник. Всё остальное лежит на диске и не занимает внимание.

Почему нельзя поставить сторонний скиллпоказать

Каталог закрытый: 21 скилл от сервиса плюс ваш личный. Скачать что-то с внешнего маркетплейса и подключить нельзя — установка идёт через инфраструктуру сервиса, не через файлы.

Что можно: взять скилл из каталога и дописать под свои правила. Так и появился mobile-reports — он собран из websites и настроен под ваш экран.

Длинные материалы под телефон

Пользователь читает с телефона (iPhone X, ~375 CSS px) и не осиливает простыни

текста в чате. Такой материал отдаётся отдельной HTML-страницей с навигацией,

а не сообщением.

Короткий ответ остаётся текстом в чате. Страница нужна, когда есть таблицы,

схемы, несколько разделов или техническое разжёвывание.

Это форк навыка websites; сборка, бандлинг, проверка и доставка — те же.

Дополнительно читай references/mobile-long-reads.md:

опорная ширина, чипы, переключение темы и плотности, схемы без картинок,

что проверять на узком экране. Содержание отчёта — по references/reports.md,

оформление новой страницы — по references/design.md.

Что должно быть на странице

  • закреплённая полоса с чипами на разделы (ссылки #id, свайп вбок);
  • переключатель светлая/тёмная — читают вечером;
  • переключатель плотности: «карточки» (воздух) и «компакт» (плотнее примерно

в полтора раза) — один экран, два варианта, без перезагрузки;

  • тезис виден сразу, разжёвывание — под спойлером <details> (см.

references/mobile-long-reads.md, раздел «Тезис + раскрытие»);

  • таблицы максимум в три колонки, блоки кода в собственной прокрутке;
  • схемы потоком из блоков со стрелками и полоски вместо столбчатых диаграмм.

Рабочий процесс

  • Собрать содержание по references/reports.md: цифры, единицы, источники.
  • Сверстать по references/mobile-long-reads.md; тему и плотность

переключать атрибутами на <html>, а не двумя отдельными файлами.

  • Проверить на 375 px: нет горизонтального скролла, чипы не ломаются,

тёмная тема сохраняет контраст.

  • Отдать файл вложением через механизм файлов. Постоянную ссылку обещать

только после отдельной публикации.

Доставка

Вложение в чат открывается встроенным просмотром мессенджера — вёрстка должна

выглядеть там же, а не только в полноценном браузере. Прочее — в

references/runtime-and-delivery.md.

Мобильное чтение длинных материалов

Режим для случая, когда отчёт будет читать человек с телефона, а не с

десктопа. Применяется вместе с reports.md: там про содержание и точность

данных, здесь — про то, как это переживает узкий экран и чтение лёжа.

Признаки, что нужен этот режим: пользователь прямо говорит «читаю с

телефона», «простыню текста не осилю», просит навигацию, схемы, чипы,

несколько вариантов оформления, или просит присылать разжёванные разборы

страницей, а не сообщением.

Опорная ширина

Целиться в 375 CSS px — это iPhone X и близкие по размеру экраны. Не

полагаться на width=device-width как на достаточное: проверять, что при

343–375 px нет горизонтального скролла, включая таблицы и блоки кода.

Практические пределы, проверенные на реальной странице:

  • база 15,5–16 px; заголовок 23–26 px;
  • отступы по краям 12–18 px;
  • таблица в три колонки помещается; четыре уже надо резать или переводить

в карточки;

  • блок кода — уменьшать кегль до 12,5–13,5 px и разрешать прокрутку только

внутри блока, не странице целиком.

Что читается на телефоне, а что нет

Хорошо: таблицы, схемы, карточки, короткие списки, выноски.

Плохо: сплошные абзацы длиннее экрана, широкие таблицы, вложенные списки на

три уровня. Сплошной текст на телефоне — самое слабое место любой вёрстки;

если материала много, дробить на блоки, а не увеличивать шрифт.

Навигация

Закреплённая полоса с чипами над контентом: position: sticky; top: 0.

Чипы — ссылки href="#id" на заголовки разделов, горизонтальная прокрутка

свайпом, scrollbar-width: none и ::-webkit-scrollbar { display: none },

чтобы полоса не занимала высоту. Чип должен иметь white-space: nowrap и

flex: 0 0 auto, иначе подписи сломаются по строкам.

На iPhone тап по чипу даёт мгновенный переход; у каждого раздела должен быть

стабильный id. При закреплённой полосе разделу нужно смещение

scroll-margin-top, иначе заголовок уедет под полосу.

Переключение темы и плотности

Оба переключателя работают без перезагрузки: атрибуты на <html>

(data-theme, data-style), правила в CSS через [data-theme="dark"] .card

и небольшой скрипт, который меняет атрибут. Не делать два отдельных HTML —

иначе пользователь не сможет сравнить варианты на одном экране.

  • тема: светлая и тёмная, кнопка наверху. Тёмная нужна не как украшение, а

потому что читают вечером;

  • плотность: «карточки» (воздух, тени, блок на раздел) против «компакт»

(плотнее в ~1,5 раза, левая цветная линейка вместо рамок). Компакт

выигрывает на длинных технических разборах, которые читают целиком.

При смене темы не забыть, что в тёмной отдельные тени и белые подложки на

глаз не читаются: заменять на var(--soft) и тонкую рамку.

Тезис + раскрытие: спойлеры

Плотность на телефоне даёт не только «карточки/компакт», но и раскрывающиеся

блоки. Приём, проверенный на реальном пользователе: сверху остаётся один тезис,

весь объём (определения, примеры, оговорки, большие таблицы) уходит под тап.

  • сворачивать: нативный <details class="sp"><summary>…</summary><div class="in">…</div></details>

— работает без скрипта, доступен скринридером, печатается в PDF;

  • маркер задавать через summary::before: «+» в свёрнутом, «–» в открытом

(details[open] > summary::before { content:"\2013" }), list-style: none и

::-webkit-details-marker { display: none } — иначе Safari покажет свой

треугольник поверх;

  • плюс, а не стрелка или треугольник: на телефоне стрелка путается с полосой

прокрутки, треугольник читается как пункт списка;

  • подпись «показать» в шапке спойлера гаснет при открытии — видно, что уже

раскрыто;

  • предупреждения — отдельный вид спойлера с цветной полосой слева: он опознаётся

свёрнутым, до прочтения;

  • одна кнопка «Раскрыть всё / Свернуть всё» на всю страницу — кто читает подряд,

не должен тапать десять раз;

  • не прятать схемы и ключевые таблицы: они и есть сообщение. Прятать текст.

Чипы полезно подсвечивать по текущему разделу через IntersectionObserver с

rootMargin: '-70px 0px -70% 0px' — видно, где находишься в длинном материале.

Схемы и диаграммы без картинок

  • поток: вертикальный список блоков со стрелкой ↓ между ними. На телефоне

вертикальная схема читается лучше горизонтальной, которая требует скролла;

  • полоски вместо столбцов, когда важен порядок величин, а не точное значение:

строка = подпись + трек + число, ширина в процентах;

  • всё собирается CSS, без внешних изображений: работает офлайн, в тёмной теме

и при печати.

Проверка

Открыть на ширине 375 px и проверить: чипы прокручиваются и не ломаются,

переключатели меняют вид без перезагрузки, ни одна таблица не выталкивает

страницу по горизонтали, тёмная тема не теряет контраст.

Собирать страницу кодом, а не писать HTML руками

Проверено на нескольких отчётах подряд: держать базовую CSS и шапку с

переключателями в одном переиспользуемом модуле (htmlkit.py в рабочей папке

проекта), а каждый отчёт писать как вызов `page(title, kicker, subtitle,

sections, footer) со списком разделов и spoiler(title, html, tip=…)`.

Почему: ручная вёрстка на третий отчёт начинает разъезжаться — забывается

white-space: nowrap у чипа, ::-webkit-details-marker, контраст в тёмной

теме. В модуле всё это задаётся один раз, а отчёт остаётся только содержанием.

Практические грабли, на которых уже спотыкались:

  • CSS со знаком % внутри строки формата %-форматирования ломает сборку —

вставлять стиль через отдельное поле, а не склеивать одной строкой.

  • Скрытый маркер <details> в Safari: без list-style: none и правила для

::-webkit-details-marker поверх плюса рисуется системный треугольник.

  • Вложенный список состояний («готов / ждёт») удобнее таблицей с бейджами,

чем абзацем: на телефоне видно одним взглядом.

Доставка

Файл отдаётся вложением в чат — в мессенджере он открывается встроенным

просмотром, и вёрстка должна выглядеть там же, а не только в полноценном

браузере. Постоянная ссылка требует публикации, а это отдельный запрос;

не обещать адрес раньше времени.

Постоянная ссылка: что важно сказать сразу

Публикация через GitHub Pages или Cloudflare Pages — отдельная задача, и до

разговора о ней стоит честно назвать два ограничения, иначе обещание

придётся забирать назад:

  • у облачной машины нет входящего адреса, поэтому «открыть файл по ссылке с

моей машины» нельзя — нужен внешний хостинг;

  • Cloudflare Pages на бесплатном тарифе не делает сайт приватным:

опубликованное доступно по адресу любому, кто его знает. Для закрытых

документов нужен Cloudflare Access (вход по почте) либо хранение ленты

внутри приватного репозитория без публикации. GitHub Pages на бесплатном

тарифе — тоже только публичный сайт.

Design for the brief

Adapted from Anthropic's Apache-2.0 frontend-design skill. Modified for

MultiTool's standalone HTML workflow.

Ground palette, typography, and composition in the subject, audience, and

primary job of the page. Use the user's actual content throughout. Where the

brief leaves room, choose a coherent direction instead of a generic template.

Where it specifies a direction, follow it precisely.

For new designs, make a compact plan before writing the page: 4–6 named color

tokens, typefaces and their roles, one layout concept, and the element that

will make this experience distinctive. Review those choices against the brief

and revise anything that would appear unchanged in an unrelated project.

Typography carries personality. Set deliberate sizes, weights, and spacing;

use one family or a clearly differentiated pair. System fonts work well for

offline artifacts; embed a font only when it adds enough value. Keep reading

lines below about 80 characters. Avoid decoration disguised as hierarchy:

unnecessary all-caps labels, italicizing a single headline word, or a label

above every section do not automatically make the content clearer.

Open with the most characteristic part of the subject: a headline, image,

demonstration, or interactive moment. Build a progression in which each

section adds substance and helps the visitor take the appropriate next step.

A richer presentation does not need unrelated application features.

Use structure to convey information. Numbering belongs to real sequences;

cards, dividers, borders, and labels should communicate relationships rather

than fill space. Avoid automatically producing the same cream / serif /

terracotta palette, black / acid-green palette, newspaper layout, or uniformly

rounded SaaS card grid regardless of the subject. These can fit a specific

brief, but they are choices rather than defaults.

Spend visual boldness in one place. Keep surrounding elements disciplined.

Motion should answer a person's action or direct attention deliberately; a

single purposeful reveal beats scattered entrances on every section. Respect

reduced-motion preferences. Build responsive layouts, readable contrast,

keyboard focus, and properly named controls without announcing them as features.

Write from the visitor's perspective. Use familiar words, active verbs, and

specific actions: a button says what will happen. Keep action names consistent

through the flow. Explain errors with a useful next step and empty states with

an invitation to act. Avoid fake testimonials, unverified numbers, and copy

that sells functionality the page does not implement.

Critique the rendered page when a browser is available. Check desktop and

mobile, the primary interaction, and whether the visual hierarchy matches the

brief. Fix what is visibly wrong and remove decoration that adds no meaning.

Reports and data pages

Adapted from MultiTool's former html-report skill; its design guidance derives

from Anthropic's Apache-2.0 frontend-design.

Use this mode for findings, comparisons, metrics, and analysis presented as

HTML. It shares the skill's export and browser checks. For a copied website or

course use snapshot mode instead: report structure must not change its content.

Content and design

Design around the actual material and audience. A useful report can have a

title with period/scope, a short answer or summary, thematic sections with

evidence, and source/methodology notes. Include headline metrics only when the

data has meaningful ones; a narrative document needs no invented KPI band.

Choose tables, charts, and prose according to what makes the evidence legible.

Read design.md for a new design, preserving any supplied branding.

Every figure must trace back to the supplied or retrieved data. Keep units,

periods, denominators, locale formatting, and comparison bases explicit.

Preserve precision; distinguish estimates and illustrative data. Check that

totals and percentages reconcile and that prose matches the figures. Missing

values are missing values, not zero. Link actual sources where useful unless

the user requested no outgoing links.

Prefer readable lines, clear hierarchy, restrained emphasis, and responsive

tables. Right-align comparable numeric columns, put units in their headings,

and avoid making color the only way to read a result. A screenshot-shaped

report is not a replacement for selectable text and semantic markup.

Charts

For small datasets, HTML tables, CSS bars, and inline SVG are portable. A

vendored/built library can also be embedded when interaction warrants it; a

CDN dependency cannot be part of an offline artifact. Avoid adding a chart

where a few values are clearer in a table.

  • Bar/column lengths must be proportional, with a zero baseline unless a

different baseline is explicitly explained. Show labels and units.

  • Line charts need honest axes, periods, labels, and gaps for missing values.
  • Pie/donut charts fit a few parts of one whole. Check the total and label

the segments; many categories usually read better as bars or a table.

  • SVG viewBox, coordinates, and stroke sizes must leave room for labels.

Give graphics an accessible title/description and keep key values available

as text, including when JavaScript is disabled for a primarily static report.

Print and verify

Set the page language and title, semantic headings, useful captions, keyboard

focus for controls, and readable contrast. Reports should print without

clipped tables or missing content. A typical starting point is:


@media print {
  body { background: white; color: black; }
  main { max-width: none; margin: 0; padding: 0; }
  nav, button, .screen-only { display: none; }
  table, figure { break-inside: avoid; }
  thead { display: table-header-group; }
}

Adapt that rule for long tables; keeping a table together must not make it

overflow the printed page. Expand report content hidden behind interactive

controls for print, and inspect the actual print rendering when possible.

Verify numbers, chart geometry, source attribution, mobile layout, and print

output. For an interactive dashboard also test its actual filters and state.
