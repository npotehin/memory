Проект: «дашборд памяти» — часть знаний консьержа хранится в Git-репозитории, пользователь видит каждое изменение.

1. Зачем

Консьерж теряет детали, когда переписка длинная и разноплановая. Память внутри сервиса есть, но пользователь её не видит и не может поправить.

Задача: сделать память видимой, редактируемой и откатываемой.

  • что помню — видно в репозитории;
  • как изменилось — видно в истории коммитов;
  • откатить — одна кнопка в GitHub.

2. Ключевое ограничение

«Подгрузи файл проекта и забудь остальное» — так не работает.

Консьерж не читает репозиторий сам по себе. Чтение — это действие, его нужно запустить.

Вывод: нужен маленький слой, который всегда на виду. Он и решает задачу.

3. Три слоя памяти

Слой Где Когда загружается Объём
1. Индекс dashboard/index.md всегда ~1 экран
2. Файл проекта projects/<slug>/PROJECT.md по названию проекта 1–2 экрана
3. Личное wiki консьержа по теме —

Почему личное отдельно

Проектные данные — можно показать и обсудить. Медицинские записи, сон, договорённости с людьми — не место в репозитории, даже приватном.

Правило: проект живёт в GitHub, личное — в wiki. Дублей не держим.

4. Структура репозитория

memory/
├── dashboard/
│   └── index.md          ← всегда в контексте
├── projects/
│   ├── rksh/
│   │   └── PROJECT.md
│   ├── ads-stack/
│   │   └── PROJECT.md
│   └── home-agent/
│       └── PROJECT.md
└── README.md

Что в индексе

| Проект | Статус | Обновлён | Файл |
|--------|--------|----------|------|
| РКШ    | активен | 25.11   | projects/rksh/PROJECT.md |

Ничего лишнего. Цель индекса — чтобы консьерж знал, что проекты существуют, и мог открыть нужный.

Что в файле проекта

  • цель в одном абзаце;
  • решения с датами;
  • открытые вопросы;
  • следующее действие;
  • журнал изменений.

5. Как обеспечивается прозрачность

Механизм Что даёт
Коммит на каждое изменение История целиком, автор и время
Осмысленное сообщение коммита «Добавил решение по MCP: read-only» вместо «update»
Блок «Журнал» в файле Дата, что поменяли, почему
Pull request для крупного Можно отклонить до слияния

Принцип: ничего важного не решается молча.

6. Практика работы

Начало проекта

«Работаем по РКШ»

Консьерж открывает projects/rksh/PROJECT.md и дальше держит в голове нужное. Телеграм-история уже неважна — ровно как задумано.

Новое решение

Консьерж правит файл, коммитит, сообщает что изменил.

Триггеры

rksh        → РКШ
ads-stack   → Метрика, Директ, MCP
home-agent  → домашний агент
memory      → сам дашборд

7. Что нужно от пользователя

Что Зачем Как
Приватный репозиторий База памяти Создать в GitHub
Токен fine-grained Доступ консьержа Один репозиторий, Contents: RW, срок 7 дней
Список проектов Стартовый индекс Диктовкой или текстом

Токен выдаётся через интерфейс GitHub, не в чат.

8. Риски

Риск Mitigation
Расхождение с wiki Проект → GitHub, личное → wiki, без дублей
Устаревший индекс Дата в каждой строке, проверка при открытии проекта
Секреты в репозитории Никогда: токены только в настройках, в файлах — ссылки
Консьерж забыл открыть файл Индекс загружается всегда

9. Следующий шаг

  1. Создать репозиторий.
  2. Положить index.md и projects/rksh/PROJECT.md — на живом примере.
  3. Прогнать один цикл: чтение → правка → коммит → просмотр истории.
