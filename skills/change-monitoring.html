Наблюдения и уведомления

Для работы с файлами, HTML и sandbox читай общую инструкцию

references/runtime-and-delivery.md.

Закрой цикл «выбрать объект → проверить источник → зафиксировать исходное состояние

→ сравнивать → уведомлять → изменить/остановить». Нативный cron владеет расписанием

и доставкой; sandbox пользователя — скриптом и состоянием. Browser-use помогает

настроить извлечение и проверить его, Scrapling — повторять извлечение без модели.

Отдельный changedetection.io, браузер, scheduler или MCP не требуются.

Выбор ветки и этапа

Выбери ветки по требуемому результату. Прочитай указанные инструкции перед

соответствующим этапом; осмотр вложений и уточнения могут предшествовать ему.

В составной задаче загружай ветки по мере перехода к этапам, а не весь пакет.

Контракт наблюдения

Возьми из запроса объект, источник, сравниваемое поле, условие, частоту и срок.

Сохрани идентичность: SKU/вариант/продавец/регион, дата поездки или спектакля,

поисковые фильтры вакансий либо конкретный раздел/папка. Не сравнивай разные

комплектации, валюты, тарифы, условия скидки или платёж в рассрочку с полной ценой.

Назови частоту проверки; обещание «сразу» ограничено ею и доступностью источника.

Не создавай постоянное задание из разового «проверь, изменилось ли».

Выбери условие: любое изменение, снижение/рост, строго ниже/выше порога,

достижение статуса, новые ID впервые или появление относительно предыдущей проверки.

Различай «ниже 30000» и «не дороже 30000»: helper поддерживает строгие пороги;

для включительной границы coder должен явно реализовать и проверить условие.

По умолчанию первый запуск создаёт baseline без объявления найденного новым.

Если пользователь просит сообщить о текущем выполнении условия, включи initial_notify.

Подготовка и запуск

Пакет содержит исполняемый scripts/watch.py и тесты. Подготовь его

через штатный skills prepare, затем используй подтверждённый путь. Helper — Python

3.10+, stdlib, без сетевых запросов, установки библиотек и собственной отправки.

Он принимает нормализованное наблюдение; получение данных выполняет отдельный

проверенный adapter в постоянном sandbox. Не называй наличие helper готовым live-монитором.

Для установки зависимостей и adapter используй штатный coder с полным контрактом.

Начни с API/RSS/HTTP, затем HTML через Scrapling; динамические страницы используют

существующий Chromium только через разрешённый lifecycle брокера.

Подробнее: references/extraction.md.

Не подключай второй клиент к занятой вкладке browser-use и не закрывай чужой context.

Сохрани отдельный каталог каждого наблюдения внутри пользовательского workspace.

Нельзя брать baseline из общей PG, чужих сессий или директории gateway.

Создай config, выполни init, проверь успешное наблюдение и diagnostic result.

Схема, режимы, команды и состояния:

references/state-and-runner.md.

Не регистрируй change-only расписание до проверки постоянного состояния и доступа

к выбранному источнику из unattended-контекста; при отсутствии возможностей честно

дай разовую проверку/сводку без обещания непрерывного наблюдения.

Для детерминированной проверки используй cron kind="script",

script="computer:~/watch/<id>/check.py". Adapter берёт свежие данные и вызывает

helper; stdout содержит только уведомление, пустой stdout — тишина. Ошибка проверки

завершает запуск ненулевым кодом; не печатай «изменений нет» при отказе сайта.

Для смысла изменений допускается native agent job со самостоятельным брифом,

skills=["change-monitoring"] и доступом к тому же состоянию. Не вызывай LLM

для обычной проверки цены. Следуй нативному cron guidance и фактическим схемам.

Валидация и эксплуатация

Перед расписанием проверь реальную страницу через browser-use, значение/единицу,

идентичность и условия; отправь полученный скриншот через send_file. Выполни повторный

запуск adapter без изменений: он должен молчать. На сохранённых fixture проверь

нужное изменение, повтор, отказ/неполный ответ, неверную валюту/объект, потерю

состояния и восстановление после перезапуска. Сценарии:

references/validation.md.

Fixture с выдуманной ценой не выдавай за реальный оффер.

Покажи, что наблюдаем, условие, расписание, источник, последний успешный результат

и статус настройки. Подтверждай создание задания фактическим ответом cron.

Изменение условий требует явного reset baseline/revision после сохранения истории;

пауза/остановка — обновление существующего задания, не создание дубля.

Наблюдение, подготовка сообщения и доставка — разные факты. Helper сохраняет событие,

но не подтверждает доставку; её проверяй через cron last_runs. При неизвестном исходе

не повторяй рассылку автономно. Повтор после подтверждённого отказа — через нативный

механизм; старое событие не объявляй новой проверкой. Если adapter сломался, сохраняй

последний хороший baseline; восстановление селектора не разрешает молча сменить товар.

Совместное применение

Этот навык — единый владелец baseline, source adapter, сравнения и событий

изменения. Предметный навык передаёт объект/источник/условие/частоту, не создаёт

параллельный watcher. Штатный cron владеет только расписанием и доставкой.

shopping-research может передать точное предложение для слежения за ценой/наличием;

travel-leisure — выбранный билет/слот; career-assistant — запрос вакансий;

news-briefing — выбранные источники/истории. Только поручение на наблюдение создаёт

расписание. krche можно использовать после подтверждённой нативной интеграции,

а не через проектируемые endpoints. Наблюдение ничего не покупает и не бронирует.

Для большого списка по запросу создай HTML со статусами, графиком проверенных цен

и изменениями; управление cron через офлайн страницу не обещай.

Извлечение и существующий браузер

Сначала выясни, откуда получить проверяемое значение: официальный API/JSON,

RSS/Atom, структурированные данные HTML, затем нужный DOM-участок.

Не скачивай весь сайт и не сравнивай полную страницу, если нужно одно поле.

Pagination должна завершиться в выбранном scope; неполный ответ не становится

полным пустым списком. Наличие cache отмечай; stale значение не выдавай за текущую цену.

Scrapling

Просмотренный upstream pyproject задаёт 0.4.15, Python >=3.10. Перед установкой

проверь наличие этой закреплённой версии и совместимость с Python sandbox;

если её нет, выбери доступный pin после чтения release notes и проверки API.

Базовый parser можно установить project-local:


uv venv .venv
uv pip install --python .venv/bin/python 'scrapling==0.4.15'

Переиспользуй уже созданный venv, не перезаписывай его. Это инструкции первой

установки, не утверждение о наличии Scrapling. Не устанавливай all/ai/shell или

ещё один Chromium ради CSS-парсинга. Готовый HTML можно разобрать через

from scrapling.parser import Selector; page = Selector(html, url=source_url);

проверяй актуальную API закреплённой версии. Для HTTP fetchers нужны дополнительные

зависимости, выбирай их только если прямого штатного HTTP/браузера недостаточно.

Для динамической страницы Scrapling поддерживает cdp_url/executable_path, но

это не доказывает разрешённый CDP-доступ из нашего cron. Сначала проверь реальный

контракт broker lifecycle/lease. По возможности бери HTML из существующей

разрешённой браузерной операции и используй parser отдельно. Не открывай порт

браузера наружу, не извлекай служебный endpoint/токен из процессов и не закрывай

browser-use context. Если unattended browser path отсутствует, не обещай такую

проверку по расписанию; HTTP/доступный API — самостоятельный fallback.

Настрой adapter через browser-use/coder: получить страницу, выбрать конкретное

поле, сверить идентичность, сформировать нормализованное observation и выполнить

с helper. Повторная простая проверка не вызывает browser-use LLM каждый раз.

Для источника, требующего входа, используй только разрешённую пользовательскую

сессию и нативные правила unattended; ручной login не гарантирует доступ cron.

Adaptive selector сохраняет признаки элемента в SQLite. Назначь storage внутри

каталога конкретного наблюдения. При перестройке DOM похожий элемент — кандидат,

не доказательство: сверяй SKU/название/вариант/тип цены и единицу. Несколько подходящих

элементов или неуверенное соответствие — check_failed, baseline не обновляется.

Автосохранение ошибочного кандидата не должно закреплять неверный селектор.

changedetection.io

Оттуда переиспользован подход: выбранный участок, нормализация, снимок → изменение,

условие уведомления. В helper upstream-код не скопирован. Их diff использует

difflib/diff-match-patch; простое typed сравнение не требует переноса UI-рендерера.

Функции условий связаны с Flask/plugins, весь runtime и собственный scheduler

нам не нужны. Если позже переносится конкретный код, закрепи ревизию, сохрани

Apache-2.0/атрибуцию/NOTICE при наличии, отметь изменения и проверь функции/зависимости.

Scrapling лицензирован BSD-3-Clause; сохраняй уведомления при распространении.

Состояние и adapter

Подготовленный watch.py можно скопировать вместе с тестами в постоянный каталог

наблюдения. Пример ~/watch/stroller/: watch.py, check.py, config.json, state.sqlite,

fixtures и выбранные скриншоты. ID каталога генерируется, не берётся как shell-код

из названия пользователя. Adapter закрывает источник, извлечение и доставку stdout,

а helper — сравнение/состояние. Дополнительного server/MCP нет.

Config


{"watch_id":"stroller","title":"Коляска — выбранная модель","entity":"sku:blue:seller1:moscow","field":"price","source_url":"https://example.com/item","unit":"RUB","mode":"below","threshold":"30000","initial_notify":false}

URL в примере — fixture, заменяется реальным проверенным URL без credentials/token.

entity кодирует сравниваемый объект, field — одно поле, unit — явную единицу/валюту

(пустая строка для безразмерного статуса/ID). Числа — целые или десятичные строки

с точкой, без символа валюты и без float. Observation должен совпасть по entity,

field, unit и source_url. Adapter сверяет их с фактическими данными, а не просто

копирует ожидаемое из config: иначе проверка идентичности бесполезна.

Режимы: change — изменение JSON-значения; decreased/increased — направление числа;

below/above — вход в строгий порог, повтор внутри зоны молчит; equals — достижение

точного JSON-статуса (true отличается от 1); added — ID, добавленные с прошлого

успешного снимка; new — ID, никогда прежде не наблюдавшиеся в этом наблюдении.

Для вакансий/публикаций обычно new; для повторного появления — added или equals.

В режиме new первый baseline засевает seen старой выдачей. Для списков ID смена

порядка и повторы не являются изменением. Для change списков порядок существенен:

adapter должен нормализовать его, когда порядок не относится к задаче.

Наблюдение


{"status":"ok","entity":"sku:blue:seller1:moscow","field":"price","source_url":"https://example.com/item","unit":"RUB","checked_at":"2025-01-01T12:00:00+03:00","value":"32000"}

checked_at — реальное время получения с offset; не дата cache/feed и не будущая дата.

value null/пропуск — ошибка, а не 0, отсутствие товара или пустая папка. Для пустого

списка нужен успешный полный ответ с value []; для отсутствия в наличии — достоверный

false или проверенный статус. status error/partial не обновляют baseline.

Старые или противоречивые наблюдения отвергаются.

Команды из каталога наблюдения:


python watch.py init --db state.sqlite --config config.json
python watch.py observe --db state.sqlite --input fixture.json --json
python watch.py status --db state.sqlite
python watch.py reset --db state.sqlite --config config.json

Для production adapter предпочтителен импорт watch.py как локального модуля,

result = watch.observe(db, observation) и print(result['message']) только при

result['notify']. Ошибки выходят stderr/ненулевым кодом; диагностический --json,

install logs и успешный init не должны попасть в stdout плановой проверки.

В script job не нужна LLM или активная беседа. Если API меняется/возвращает login,

CAPTCHA, 429 или другой объект, adapter завершает проверку ошибкой и сохраняет

baseline. Возобновление после смены критериев требует reset и новой revision.

Вызов init для существующего наблюдения отвергается; observe не создаёт отсутствующую

DB. Reset сохраняет события, очищает baseline и seen. Это новый контракт сравнения.

SQLite transaction сериализует операции, сохраняет последний хороший снимок и

сообщения при срабатывании. History растёт по событиям, а не по каждому unchanged

запуску; status показывает последние 20. Полные HTML и скриншоты сохраняй выборочно,

retention согласуй с задачей. Повреждённое/потерянное состояние нельзя незаметно

заменить новым baseline. Восстанавливай его из доступной резервной копии либо

объясни разрыв истории и создай новый контракт по поручению.

Доставка и повторы

notify — подготовленное сообщение, не delivery receipt. Штатный cron/Temporal

управляет выполнением и доставкой, helper не обращается к платформам. У события

есть event_id; одинаковое наблюдение не создаёт повтор, выход и повторный вход

в порог могут создать новое событие. Сохранение события и вывод stdout — не одна

атомарная транзакция: crash между ними требует проверки истории и нативного

результата выполнения. Не обещай exactly-once delivery только на основании SQLite.

last_runs — источник статуса доставки; не помечай историю как delivered из факта print.

Валидация наблюдения

Helper и adapter

Тесты пакета проверяют stdlib helper на fixture без внешних сайтов. Они не доказывают

доступность реального источника, browser lifecycle или доставку в мессенджер.

Для конкретного adapter coder создаёт небольшой воспроизводимый тест на сохранённых

ответах: нормальный результат, нужное изменение и источник без ожидаемого поля.

Сохраняй реальные идентификаторы; личные токены, cookies и данные других людей

в fixture не включай.

Проверь:

  • Первый успешный снимок — baseline; initial_notify выполняет выбранную политику.
  • Unchanged/повторы/разный порядок ID — тишина. «30000.00» и «30000» сравнимы.
  • Порог — нужная граница; повтор внутри зоны молчит; после выхода новое достижение

допустимо. Режим decreased уведомляет о каждом новом снижении, это иной контракт.

  • Новые вакансии/публикации — режим new; исчезновение/возвращение старого ID не

рождает новую запись. Для повторного появления — added.

  • Другая валюта/товар/поле/дата тарифа — comparison_unavailable, baseline сохраняется.
  • Login page, отсутствующая цена, CAPTCHA, timeout, partial pagination — check_failed.

None не превращается в 0/false/пустой список.

  • Потеря DB — сравнение недоступно; baseline не пересоздаётся автоматически.
  • Изменение критериев — явный reset/new revision, история событий сохранена.
  • Повтор процесса читает сохранённое состояние; concurrent checks сериализуются;

запоздавший снимок не заменяет новый.

  • Два пользователя с одним URL/watch_id используют разные sandbox/DB.

Проверка реального источника

Проверь фактическую страницу через native browser-use и передай screenshot.path

через send_file. Сверь выбранную сущность, тип значения, валюту, регион, условие

и timestamp adapter. Выполни две реальные проверки adapter: вторая молчит,

если изменения действительно не было. Для контролируемого изменения используй

отдельную fixture/test DB, не меняй цену на живом сайте и не подменяй baseline.

Из unattended-контекста проверь доступ к тому же workspace и source, затем native

cron run/last_runs. Если требуется тестовое уведомление, явно подпиши «тест» и

используй delivery только в авторизованный исходный чат. Нельзя автоматически

создавать периодическое наблюдение/писать пользователю ради проверки самого пакета.

Проверка подготовки файла, публикация skill, запуск adapter, результат сравнения

и подтверждённая доставка — разные этапы. При неизвестном delivery outcome сначала

проверь last_runs, не повторяй самостоятельно. При сбое между фиксацией события

и stdout используй сохранённый event_id/message для восстановления через нативный

workflow; восстановленное сообщение не называется новым изменением.

Визуализация по запросу

HTML показывает список наблюдений, условия, последний успешный снимок, историю

значений/событий и отдельные ошибки проверок из реальных журналов. История helper

содержит сработавшие события и текущий snapshot, не все измерения: график нельзя

выдавать за непрерывный ценовой ряд. При необходимости adapter сохраняет успешные

измерения отдельно с provenance и timestamp. Пропуски не интерполируются как факты.

Нужны фильтры, раскрываемое «было → стало» и прямые ссылки. Проверяй страницу через

browser-use; pause/remove кнопки без реальной интеграции не обещай.

Среда, проверка и доставка

Читай для файлов, интерактивного HTML или исполнения задачи; уже прочитанную

общую инструкцию в текущей беседе повторно не загружай. Предметные критерии

проверки определяет выбранный навык.

Объём работы и среда

Простой ответ, короткий черновик, обычный рецепт или расчёт выполняй в чате.

Создавай HTML для сложного плана, сравнения, динамики или по запросу; один пункт

не требует страницы. Файл в заказанном формате остаётся обязательным.

Переиспользуй native web/vision/STT, coder/исполнение, browser и sender.

Проверяй реально выданные инструменты и их схемы. Не создавай второй scheduler,

browser runtime или sender. API/MCP используй только при доступном подключении;

допуск стороннего MCP требует >1000 GitHub-звёзд, официальные API разрешены напрямую.

Файлы и зависимости находятся в личной sandbox, не в gateway. Skills prepare

возвращает путь пакета; пути вложений получай через штатный импорт/список файлов.

Путь для vision и байты для обработки могут требовать разных инструментов.

Установи только зависимости нужной ветки в проектную среду при первом вызове;

переиспользуй рабочие версии, сохраняй lockfile и оригиналы. Личные устройства

и аккаунты не становятся доступными из облачной sandbox автоматически.

Проверка

Проверь сохранённый итоговый файл, независимые расчёты и необходимые предметные

условия. HTML проверяй headless через доступный browser-use/Chromium: реальные

действия, связанные показатели, empty/error states, desktop/mobile и console.

Сохрани настоящие скриншоты. Снимок другого представления не доказывает качество

DOCX/PDF/PPTX, статичный кадр — плавность анимации. Детали рендера задаёт форматная ветка.

Долгую работу веди штатно с реальным job/operation handle. Проверяй существующую

операцию, не запускай дубль при busy/pending. Сохраняй exit code и связывай проверку

с актуальной версией файла; отменённая проверка остаётся непроверенной.

Инструкции при передаче исполнителю

В задании coder/другому исполнителю укажи точный skill_ref из успешного чтения

и пути references для текущего этапа. Исполнитель должен прочитать SKILL.md и эти

references перед предметной работой: по закреплённой версии через native read

или из пакета, подготовленного по тому же skill_ref. Укажи результат, входные

материалы и критерии проверки. Не считай одно название навыка доказательством

прочитанных инструкций; при новом этапе загружай только нужную ветку.

Состояние и передача

Страница без backend показывает snapshot. Не обещай live chat, общую историю или

автоматическое сохранение: дай экспорт и проверяемый путь импорта в личный workspace,

если они нужны. Не помещай секреты в HTML/архив и не публикуй личные данные по умолчанию.

Передай заказанный файл штатным sender по подтверждённому пути. Скриншоты

отправляй по запросу или когда они помогают объяснить результат; сохранение

скриншотов для QA само по себе не требует их доставки.

Локальный путь или localhost не являются пользовательской ссылкой. Login/captcha

передавай через штатный handoff. Неизвестный исход внешней операции сначала проверь

по фактическому состоянию. Создание файла не разрешает покупку, отправку или запись.

Календарь, порученные напоминания и доставка остаются native. Наблюдение за

изменениями передавай change-monitoring с объектом, источником, условием и частотой;

он владеет baseline/сравнением, штатный cron — расписанием и доставкой.
