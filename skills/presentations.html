Презентации HTML и PowerPoint

Для работы с файлами, HTML и sandbox читай общую инструкцию

references/runtime-and-delivery.md.

Используй OpenSlide для всех презентаций и прочитай references/openslide.md перед работой. Передай результат в запрошенном формате и исходный проект. Не обещай визуальную проверку PPTX, если смог только открыть ZIP/XML.

Содержание и форма

Определи аудиторию, желаемое решение и длительность выступления. Материалы пользователя и его шаблон важнее дефолтного стиля. Для новой истории прочитай references/storytelling.md. Сначала сформулируй обещание зрителю, центральный вопрос и развязку. Строй причинные переходы, а не список тем. Название слайда должно выражать вывод, когда это соответствует жанру; числа и цитаты должны иметь источник.

Один слайд — одна ясная задача. Для новой презентации наметь последовательность слайдов: вывод → доказательство → композиция. Сценовую карту с изменениями на экране добавляй для анимированного показа. Для выразительного дизайна и анимации прочитай references/design-motion.md. Перестановка одинаковых карточек не создаёт разнообразия. Чередуй содержательные макеты: тезис с иллюстрацией, сравнение, график, схема, последовательность, вывод. Не превращай документ в уменьшенный текст на слайдах. Подробности вынеси в заметки докладчика/приложение. Держи общими палитру, шрифты, сетку и отступы; выбирай визуальную плотность под аудиторию.

Создавай слайды в проекте OpenSlide и используй его экспорт для запрошенного формата.

Для выразительного визуального рассказа, истории создания или запроса «красиво, динамично, с эффектами» прочитай references/cinematic-scenes.md. Это проверенный подход к сценам и ритму; адаптируй его к теме и бренду. Не ограничивайся базовым fade, когда задача требует показать процесс, масштаб или смену состояния.

Редактирование

Для проекта OpenSlide осмотри всю исходную презентацию и перечисли слайды, которые меняются. Если передан только PPTX без исходного проекта, сначала проверь, возможно ли сохранить его содержимое и структуру через OpenSlide; обозначь ограничение до внесения изменений. Сохраняй остальные слайды, заметки, бренд и структуру. Проверяй длинные замены на реальном рендере. Если OpenSlide не сохраняет важный объект, обозначь ограничение до потери данных.

Готовность

  • Сопоставь содержание с задачей, проверь числа, ссылки, подписи осей и единицы.
  • Отрендери и просмотри каждый слайд: текст не обрезан, элементы не пересекаются случайно, шрифты/картинки загружены, диаграммы читаются.
  • Осмотри контактный лист: повторяющиеся композиции и отсутствующая кульминация видны на нём лучше. Для анимации проверь начало, промежуточные кадры и завершение, следующий клик во время входа, быстрый переход вперёд/назад и повторный вход. Статичный скриншот не доказывает плавность. Проверь reduced motion и конечное состояние печати. LibreOffice/PDF не подтверждают движение в PowerPoint.
  • Исправь обнаруженные проблемы и повторно просмотри затронутые слайды.
  • Проверь файл повторным открытием и фактический способ показа: HTML — навигация/полный экран/печать; PPTX — заметки, редактируемые объекты и рендер после открытия.

Передай HTML или PPTX, при необходимости PDF для просмотра и исходный проект. PDF/картинки не заменяют запрошенный редактируемый PPTX. Если проверен только один формат, не переноси эту гарантию на другой.

Презентации OpenSlide

Для любой презентации подготовь текущий пакет и создай проект в новой

папке командой node "$SKILL/scripts/gigatool/openslide/init.cjs" "$PROJECT".

Проект содержит закреплённый lockfile и пример TSX. Выполни npm ci из

папки проекта, замени демонстрационные слайды в slides/ и выполни

npm run build. Для проверки запусти npm run preview в штатной

песочнице и открой страницу через браузер Геры.

Для запрошенного PowerPoint используй встроенное меню Download → Export as

История, которая ведёт зрителя

Сформулируй одно предложение: «После презентации зритель поймёт/выберет …, потому что …». Затем вопрос, ответ на который нельзя получить уже на первом слайде. Открытие даёт обещание и причину смотреть; финал отвечает на него. Проверяй фактические материалы до драматизации.

Выбери двигатель

  • Предложение: текущее положение → цена проблемы → возможное будущее → доказательства → выполнимый следующий шаг. Контраст «сейчас / возможно» по Duarte полезен для убеждения; не растягивай его на каждый слайд.
  • История создания/биография: цель героя или команды → ограничение → выбор → последствия → следующая трудность → результат. Герой принимает решения, это не обязательно главный персонаж фильма. Не приписывай реальным людям мысли, страхи и мотивы без источника.
  • Объяснение/исследование: загадка → конкурирующие гипотезы → наблюдение → что оно меняет → границы вывода. Не маскируй отсутствие данных эффектной развязкой.

«Путь героя» — возможная модель, а не обязательные двенадцать этапов. Техническому рассказу часто достаточно цели, препятствия, решения и изменения. Story Spine помогает связать события: соедини сцены словами «но», «потому что», «поэтому». Если везде подходит только «затем», это пока оглавление.

План до слайдов

Для каждой сцены запиши: вопрос зрителя → новый вывод → доказательство → визуальное действие → следующий вопрос. Удаляй сцены, которые не меняют понимание. Подробности идут в заметки/приложение. Обещая показать, как сделан эффект, показывай процесс, а не только готовый кадр.

Пример: «Как продолжить узнаваемый мир?» → «Одного неона недостаточно» → «Нужен физический свет и масштаб» → «Как строятся миниатюры?» → «Что добавляет композитинг?» → «Почему сложный эффект может быть незаметен?» → ответ исходному вопросу. Это схема авторского объяснения, не готовые исторические утверждения.

Кульминация соединяет ранее показанные решения в одном примере. Финал возвращает начальный образ/вопрос с новым пониманием. Награды подтверждают результат, но не заменяют ответ. Избегай сюжетных спойлеров, когда рассказ о производстве обходится без них.

Проверка плана

Может ли зритель пересказать центральную мысль? Ясно ли, кто действует, чего добивается и что ограничивает выбор? Каждый ли технический факт отвечает на «зачем»? Есть ли причинная связь и оплачено ли обещание открытия? Не придуманы ли эмоции, цитаты или конфликт ради дуги?

Первоисточники подходов

Рекомендации — прикладная адаптация, а не копирование методик целиком:

  • Duarte: business storytelling — центральная идея, ставки и контраст.
  • Pixar / Khan Academy: story structure — структура и причинная последовательность.
  • Andrew Stanton / TED: The clues to a great story — причина сопереживать и осмысленная развязка.

Дизайн сцены и движение

Разнообразие с сохранением стиля

Составь контактный лист макетов до деталей. Выбирай композицию по доказательству: полноэкранный документальный кадр; число со шкалой; управляемое сравнение; последовательность; схема процесса; галерея артефактов; разбор изображения; временная линия; тихая финальная сцена. Не применяй все приёмы без необходимости. Одинаковые блоки с разными цветами не становятся разными макетами.

Таймлайн содержит события, направление и смысл связи. Расстояния соответствуют времени либо явно обозначены как схематичные. Для параллельных этапов полезны дорожки. Не выдумывай даты ради равномерной сетки.

Сохраняй реальные изображения локально с URL и подписью. Фото, модель, concept art, CG-pass и финальный кадр — разные свидетельства. До/после допустимо для сопоставимых изображений одного объекта/кадра. AI-иллюстрация маркируется как реконструкция; она не подтверждает факт. Декоративные изображения бери из ресурсов или imagegen; программные SVG используй для настоящих схем/данных, не вместо иллюстраций.

Карта движения

Запиши: объект, начальное/конечное состояние, триггер, длительность и смысл. Движение показывает причинность, время, масштаб или сравнение. Примеры: линия времени достраивается; свет проходит по технической схеме; маска открывает реальный render-pass; слои композитинга собираются; масштаб изображения меняется до появления подписи.

Заголовок — опора чтения. Обычно оставляй его неподвижным и открывай прозрачностью/маской. Не назначай всем заголовкам translateY, bounce, посимвольный stagger или glitch. Краткий эффект уместен на одной сцене, но не должен мешать чтению. Избегай постоянно движущихся фонов и резкого мерцания.

Ориентир: короткий вход 400–800 мс, объясняющее движение примерно 1–3 секунды с управлением зрителем. Это не квоты: темп определяется задачей. Переход главы и развитие внутри слайда — разные операции. Не заставляй ждать длинную заставку при каждом клике.

HTML: владение и прерывание

  • Один владелец анимаций сцены; отменяй только его handles, никогда document.getAnimations() целиком.
  • Не отменяй вход при раскрытии фрагмента: отмена WAAPI сбрасывает действующий transform и вызывает скачок. Смена слайда очищает прежнюю сцену; следующий шаг добавляет независимую группу.
  • Layout-root сохраняет центрирование/масштабирование. Для transform используй внутренний motion-wrapper. CSS и WAAPI/GSAP не должны одновременно владеть одним transform.
  • Конечные состояния существуют в CSS/DOM без анимации. Не оставляй текст невидимым до callback. Reset при повторном входе явный. Для взаимодействия допускается управляемая перемотка/реверс вместо резкой отмены.
  • Дождись шрифтов и картинок до измерений. Reduced motion сохраняет информацию и навигацию. Печать показывает конечный смысл каждого слайда.

Нативная Web Animations API подходит лёгкому offline-показу. Для сложной синхронизации используй доступный runtime локально; не добавляй библиотеку ради fade. API: MDN Web Animations, Animation.cancel, prefers-reduced-motion.

Временная проверка

Осмотри старт, четверть, середину и конец нового эффекта; сними короткую запись сложной сцены. Проверь клик во время входа, быстрое листание, возврат, toggle motion и вкладку без фокуса. У неподвижного заголовка сравни координаты до/после клика: изменение позиции означает ошибку. Следи за наложениями и читаемостью промежуточных кадров.

Автопроверки ловят переполнение, пропавшие картинки и утечки анимаций; эстетика и история требуют просмотра. Отчёт перечисляет проверенное, а не обещает «10/10». PowerPoint требует отдельных нативных объектов/переходов и проверки в целевом проигрывателе; анимация HTML не переносится автоматически.

Выразительная презентация: проверенный подход

Подход проверен на рассказе о производстве Blade Runner 2049 и одобрен пользователем. Переиспользуй логику, композиции и качество движения; тема фильма, оранжевая палитра и число слайдов не становятся обязательными для остальных презентаций.

Из замысла в сцену

Открытие показывает впечатляющий результат и задаёт вопрос «как это стало возможным?». Дальше представь участников, цель и ограничения. Показывай решения через реальные материалы: процесс, артефакты, масштаб, механизмы и изменение состояния. Свяжи их в кульминации. В финале верни начальный образ с новым пониманием.

В деловой презентации тот же приём может начинаться с результата продукта, объяснять решения и завершаться предложением. В учебной — начинаться с явления, показывать механизм и возвращаться к объяснённому явлению. Выбирай подходящую структуру из storytelling.md.

Композиции, которые можно сочетать

| Задача сцены | Композиция | Движение с назначением |

|---|---|---|

| Обещание и финальный ответ | Полноэкранное фото/кадр; крупная короткая типографика; локальный градиент под текстом | Конечный мягкий camera push на изображении, неподвижный текст |

| Сформулировать проблему | Просторная типографическая сцена; один вопрос или напряжение между двумя состояниями | Раскрытие ключевой мысли по клику |

| Показать участников/артефакт | Большое фото занимает примерно половину сцены; краткие роли/контекст рядом | Маска открывает изображение, подписи появляются спокойно |

| Объяснить развитие во времени | Связная линия событий; при необходимости параллельные дорожки | Линия достраивается; события раскрываются в нужном порядке |

| Передать масштаб | Крупное число + реальный объект + единица измерения/сопоставление | Изображение или шкала раскрываются; число остаётся читаемым |

| Объяснить механизм | Реальное свидетельство рядом с подписанной технической схемой | Движение показывает работу механизма: направление света, поток, сборку |

| Показать материальность | Галерея с разными пропорциями изображений, короткие предметные подписи | Умеренно разнесённое по времени раскрытие фотографий |

| Сопоставить состояния | Два сопоставимых изображения/данных либо большая управляемая область сравнения | Wipe/crossfade/ползунок, если исходники действительно позволяют сравнение |

| Разобрать эффект | Процесс/геометрия/слои и итог; подписи различают стадии | Управляемая сборка; один краткий характерный эффект на изображении |

| Соединить доказательства | Один сильный пример и краткая смысловая последовательность | Составляющие раскрываются и сходятся в общей мысли |

Переход между сценами меняет визуальный режим: плотное/просторное, тёмное/светлое, предметное/типографическое, статичное/объясняющее движение. Один стиль связывает их, но не требует одного макета. Повтор композиции открытия в финале может быть осмысленным возвращением.

Визуальный ориентир

Для сцены 1280×720 удачная исходная сетка: поля около 64 px; заголовки примерно 50–75 px, обычный текст 23–30 px; крупные числа могут занимать существенную долю сцены. Заголовок не должен занимать место доказательства. Второстепенные кредиты допустимо сделать меньше, основной вывод — нет. Эти значения адаптируются после реального рендера.

В проверенном примере использовались тёплый почти чёрный фон, светлый текст, янтарный акцент и светлые предметные сцены. Для другой темы выбери подходящую палитру; держи основной текст контрастным, число акцентов небольшим, а фактуру — в настоящих изображениях. Не накладывай одинаковые декоративные эффекты на каждый слайд.

Динамика без дёрганости

Заголовки держат позицию. Более заметное движение происходит в изображениях, схемах и переходах состояния. Fade подходит подписи; процессу нужен эффект, который показывает процесс. Краткое стилистическое расслоение уместно для цифрового сбоя, но не для всех заголовков. Длинное объяснение должно управляться зрителем; разреши повтор сцены и отключение движения.

Используй навигацию и управление анимациями OpenSlide; сценовые эффекты согласуй с его жизненным циклом. Проверяй, что их последняя поза совпадает с CSS/DOM: по завершении анимации объект не должен возвращаться скачком. Переход к следующему фрагменту оставляет вход текущей сцены в покое. Подробности реализации и проверки — в design-motion.md.

Что передавать для оценки

Самостоятельный HTML с локальными ресурсами, статичный PDF при необходимости, контактный лист и короткую реальную запись сложных эффектов. Дай управление и реальные ссылки на источники. В печать попадает полный смысл каждого слайда. Проверяй клавиатуру также после клика по кнопке: фокус на toolbar не должен выключать стрелки/Home/End.

Смотри не только на отсутствие переполнения: действительно ли виден механизм, чувствуется ли масштаб, понятен ли переход мысли и отличается ли композиция от соседней? Сохраняй доказательность: нельзя заменять производственный материал красивой реконструкцией или выдавать разные кадры за точную пару до/после.

Среда, проверка и доставка

Читай для файлов, интерактивного HTML или исполнения задачи; уже прочитанную

общую инструкцию в текущей беседе повторно не загружай. Предметные критерии

проверки определяет выбранный навык.

Объём работы и среда

Простой ответ, короткий черновик, обычный рецепт или расчёт выполняй в чате.

Создавай HTML для сложного плана, сравнения, динамики или по запросу; один пункт

не требует страницы. Файл в заказанном формате остаётся обязательным.

Переиспользуй native web/vision/STT, coder/исполнение, browser и sender.

Проверяй реально выданные инструменты и их схемы. Не создавай второй scheduler,

browser runtime или sender. API/MCP используй только при доступном подключении;

допуск стороннего MCP требует >1000 GitHub-звёзд, официальные API разрешены напрямую.

Файлы и зависимости находятся в личной sandbox, не в gateway. Skills prepare

возвращает путь пакета; пути вложений получай через штатный импорт/список файлов.

Путь для vision и байты для обработки могут требовать разных инструментов.

Установи только зависимости нужной ветки в проектную среду при первом вызове;

переиспользуй рабочие версии, сохраняй lockfile и оригиналы. Личные устройства

и аккаунты не становятся доступными из облачной sandbox автоматически.

Проверка

Проверь сохранённый итоговый файл, независимые расчёты и необходимые предметные

условия. HTML проверяй headless через доступный browser-use/Chromium: реальные

действия, связанные показатели, empty/error states, desktop/mobile и console.

Сохрани настоящие скриншоты. Снимок другого представления не доказывает качество

DOCX/PDF/PPTX, статичный кадр — плавность анимации. Детали рендера задаёт форматная ветка.

Долгую работу веди штатно с реальным job/operation handle. Проверяй существующую

операцию, не запускай дубль при busy/pending. Сохраняй exit code и связывай проверку

с актуальной версией файла; отменённая проверка остаётся непроверенной.

Инструкции при передаче исполнителю

В задании coder/другому исполнителю укажи точный skill_ref из успешного чтения

и пути references для текущего этапа. Исполнитель должен прочитать SKILL.md и эти

references перед предметной работой: по закреплённой версии через native read

или из пакета, подготовленного по тому же skill_ref. Укажи результат, входные

материалы и критерии проверки. Не считай одно название навыка доказательством

прочитанных инструкций; при новом этапе загружай только нужную ветку.

Состояние и передача

Страница без backend показывает snapshot. Не обещай live chat, общую историю или

автоматическое сохранение: дай экспорт и проверяемый путь импорта в личный workspace,

если они нужны. Не помещай секреты в HTML/архив и не публикуй личные данные по умолчанию.

Передай заказанный файл штатным sender по подтверждённому пути. Скриншоты

отправляй по запросу или когда они помогают объяснить результат; сохранение

скриншотов для QA само по себе не требует их доставки.

Локальный путь или localhost не являются пользовательской ссылкой. Login/captcha

передавай через штатный handoff. Неизвестный исход внешней операции сначала проверь

по фактическому состоянию. Создание файла не разрешает покупку, отправку или запись.

Календарь, порученные напоминания и доставка остаются native. Наблюдение за

изменениями передавай change-monitoring с объектом, источником, условием и частотой;

он владеет baseline/сравнением, штатный cron — расписанием и доставкой.
