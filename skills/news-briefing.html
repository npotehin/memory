name: news-briefing

description: >-

Готовить персональные и тематические новостные сводки за период: объединять инфоповоды, проверять новизну и источники; по запросу выпускать регулярно. Одна новость или уведомление об изменении страницы не требует редакционного дайджеста.

---

Персональные дайджесты

Для работы с файлами, HTML и sandbox читай общую инструкцию

references/runtime-and-delivery.md.

Дай человеку понятную картину выбранного периода: что произошло, что изменилось,

почему это относится к его интересам и где прочитать первоисточник. Используй

нативные web/search/extract, recall, доступные источники и доставку файлов.

Скилл задаёт редакционный процесс; сборщик лент и планировщик остаются штатными.

Выбор ветки и этапа

Выбери ветки по требуемому результату. Прочитай указанные инструкции перед

соответствующим этапом; осмотр вложений и уточнения могут предшествовать ему.

В составной задаче загружай ветки по мере перехода к этапам, а не весь пакет.

Задание и персонализация

Возьми из запроса и доступного контекста темы, компании/людей, регион, язык,

источники, исключения, глубину и период. Не требуй онбординга для разовой сводки.

Если темы не заданы, собери разнообразную общую подборку и коротко обозначь охват.

Явно заданные источники сохраняй; дополнительный web используй для проверки,

помечая новости вне выбранной коллекции. Личные интересы сохраняй штатной memory

при её доступности; содержимое выпусков туда не записывай. Не обещай память между

сессиями, если доступного постоянного состояния нет.

Разреши относительный период по текущей дате и часовому поясу пользователя.

Зафиксируй начало, конец и время проверки. «Сегодня» — местный календарный день,

«последние сутки» — скользящие 24 часа. Для неуточнённого «за неделю» используй

последние семь дней и покажи границы. Время проверки может предшествовать концу

запрошенного периода: будущую часть не объявляй покрытой.

Поиск, доказательства и отбор

Сначала найди кандидатов, затем проверь существенные утверждения в самих материалах.

Следуй нативной маршрутизации многоисточникового research/background: передавай

полный бриф в существующий исследовательский инструмент, если он доступен.

Не расширяй toolsets concierge и не повторяй pending/busy-задачу ради результата.

Для каждой новости различай событие, публикацию, обновление страницы и время

получения. Новая дата страницы не делает старое событие новым. У старой истории

включай только конкретное существенное изменение за период; старый контекст помечай.

Неизвестную дату не восстанавливай по URL, позиции в поиске или относительной метке.

Подробности: references/sources-and-evidence.md.

Объединяй перепечатки одного события в один пункт. Проверяй совпадение участников,

предмета и фактического изменения; разные релизы одной компании не обязательно

дубли. Отдельное подтверждение, опровержение или новый этап могут стать обновлением

истории. Несколько пересказов одного пресс-релиза не являются независимыми источниками.

Отбирай по соответствию интересам, значимости изменения и качеству доказательств.

Число пунктов адаптируй к запросу: не заполняй квоту слабыми или старыми новостями.

Разделяй «заявлено/анонсировано», «выпущено/доступно», «независимо подтверждено»,

«слух/мнение» и «опровергнуто». Заявление компании подтверждает само заявление,

но не обещанные результаты. Объяснение последствий маркируй как вывод, когда оно

не следует непосредственно из источника; фактическую сводку не подменяй советом.

Результат и продолжение

Начни с наиболее важных изменений. Каждый пункт содержит конкретное событие,

краткое объяснение значимости и прямую ссылку; добавь дату там, где она проясняет

хронологию. Для спорного сообщения укажи статус и основание, сохрани противоречия.

Назови существенные пропуски покрытия: недоступные источники, обрезанный текст,

проверка только заголовков. Если новостей не найдено, так и сообщи в рамках

проверенного охвата; отказ источника не доказывает отсутствие событий.

«Подробнее о втором» продолжает выбранную историю; «ещё» исключает уже показанные

события. Для крупных подборок или запроса страницы создай интерактивный HTML:

references/interactive-briefing.md.

При доступном sandbox используй штатный browser-use для проверки страницы и

существенных спорных ссылок; полученные скриншоты отправляй через send_file.

Для обычной короткой сводки HTML не обязателен.

Повторные выпуски и источники

По поручению на регулярную доставку используй cron с kind="agent" и

skills=["news-briefing"]. Промпт должен быть самостоятельным: будущий запуск

не наследует эту беседу. Формирование задания, сравнение выпусков и проверка

расписания: references/recurring-briefings.md.

Разовая сводка сама по себе не создаёт подписку.

Если доступны подключённые персональные news tools, RSS/Atom или MCP, используй

их в пределах подтверждённой возможности и личности пользователя. Иначе работай

через web. Для больших документов/транскриптов переиспользуй source-research;

ветку получения video-audio — для доступных субтитров, а не обещания просмотра

видео по заголовку. Запрос «уведомляй при изменении этой страницы/новом ID»

передавай change-monitoring; редакционный выпуск остаётся news-briefing.

Выбор источника и будущая интеграция krche:

references/source-integrations.md.

Источники, даты и события

Карточка при исследовании

Для отобранного кандидата сохрани: заголовок события, участников, тему/регион,

что конкретно изменилось, дату события (или unknown), даты публикации/обновления,

часовой пояс дат при наличии, checked_at, прямые URL и источник каждого существенного

утверждения. Отдельно — статус сообщения и ограничения проверки. Эти поля нужны

для отбора и сравнения; не перегружай ими каждую короткую реплику.

При ссылках из ленты сохрани source_id/item_id и исходный URL. Извлечение полного

текста не означает, что он новее ленты. Заголовок/описание могут подтверждать только

видимые в них сведения; недоступную статью не пересказывай как прочитанную.

Свежесть

  • Дата в RSS/Atom — дата записи, а не автоматически дата описанного события.
  • «Обновлено сегодня» у справки о прошлогоднем запуске не попадает в сводку запусков

за сегодня, если содержательного нового факта нет.

  • Если событие вчера, а публикация сегодня, для дайджеста событий за сегодня это

старый контекст. Для явно заказанного дайджеста публикаций за сегодня оно допустимо

с указанием даты события. По умолчанию отбирай изменения, произошедшие за период;

поздно раскрытый факт обозначай «стало известно», сохраняя историческую дату.

  • Объявленная будущая дата — план, не состоявшееся событие. Отмена или перенос

анонса может быть свежим событием сам по себе.

  • Не включай публикацию с неизвестной датой как доказанно свежую. При важности

покажи её отдельным контекстом с неизвестной датой, без утверждения о новизне.

Для развивающихся событий проверь последние доступные обновления на checked_at.

Сохрани исправления/опровержения, даже если они меняют прежний вывод.

Кластеры событий

Сопоставляй субъект + действие/изменение + объект/версию + период. Канонический URL,

ID материала, одинаковый заголовок и текст — подсказки, а не окончательное решение.

Не удаляй значимые параметры URL: ID видео, статьи и записи важны для идентичности.

Убирай только известные tracking-параметры. Разные URL могут вести на перепечатку;

один URL может позже получить исправление.

Выбери наиболее полный первоисточник и при необходимости независимую проверку.

Заявление пресс-службы и пять публикаций, ссылающихся на него, образуют одно семейство

доказательств. Не усредняй несовместимые числа: покажи, кто их сообщил, на какую

дату и с каким определением метрики. Предпочитай исправленную версию, сохраняя

ссылку на исправление и объяснение, если прежняя версия уже вошла в выпуск.

Специальные подборки

Компания/продукт: release notes, официальное объявление, фактическая доступность

и независимый опыт могут описывать разные стадии. «Обещают функцию» не равно

«функция доступна всем». Сравнение ограничений опирается на проверенные документы.

Исследования: различай препринт, рецензируемую публикацию и пресс-пересказ;

указывай существенные ограничения эксперимента. Не делай медицинских/финансовых

рекомендаций из новости без отдельного запроса и соответствующей проверки.

Видео/подкасты: используй реальный ID, название, дату и доступный транскрипт.

Из описания выпуска нельзя вывести его содержание. Привязывай выводы к таймкодам,

если их удалось получить; иначе обозначай отсутствие транскрипта.

GitHub: различай Trending, новые releases и активность за период.

Общее число stars не является приростом за неделю; текущий список Trending —

не исторический рейтинг. Репозитории объединяй с описываемыми релизами, если

это один инфоповод; не заводи отдельный skill на каждый такой источник.

Регулярные и повторные выпуски

Предпочтения и история

Предпочтения — темы, источники, исключения, регион, язык и глубина — храни через

доступный штатный механизм профиля/memory. Для cron включай их актуальную копию

в prompt; изменение memory не обновляет уже созданное задание. По просьбе изменить

подписку найди именно её через cronjob list и обнови prompt/schedule/skills.

Отмена или пауза меняет существующее задание, а не создаёт ещё одно.

Для сравнения выпусков сначала используй доступную историю этого пользователя

и этого дайджеста через session_search; не читай чужие сессии или общую cron-историю.

Сам cron-запуск не получает беседу автоматически. Если постоянный пользовательский

sandbox доступен и в очередном cron-контексте, можно хранить отдельный JSON-файл

для конкретной подписки. Путь должен быть внутри sandbox пользователя, а не gateway.

Минимальные поля записи: briefing_id, темы/источники/исключения, timezone, window,

checked_at, edition_id, события с устойчивым event_key, URL/item_id, кратким набором

уже включённых фактов и состоянием draft/completed. В completed переводится только

собранный, проверенный выпуск. Записывай через временный файл и атомарную замену;

при одновременных запусках нужен доступный файловый lock или штатное хранилище.

При потере/повреждении файла не затирай старые данные и не объявляй сравнение успешным.

completed означает «выпуск подготовлен», а не «сообщение доставлено или прочитано».

Для проверки доставки используй фактический результат штатного cron last_runs.

Неизвестный исход доставки не разрешает самостоятельную повторную рассылку.

Если история/состояние недоступны, сделай сводку за заданный интервал и обозначь,

что сравнение с прошлым выпуском не выполнено. Не обещай отсутствие повторов между

запусками; при этом внутри текущего выпуска объединение дублей остаётся обязательным.

В rolling-окне подавляй уже включённые факты, сохраняя существенные новые стадии

той же истории. Явный запрос повторить или обозреть весь период отменяет это подавление.

Задание планировщику

Следуй актуальному нативному guidance cronjob. Для дайджеста kind="agent", а не

reminder; в skills передай news-briefing. Schedule/timezone вычисляй по контексту

и явным предпочтениям пользователя. Deliver по умолчанию не задавай: штатная

маршрутизация вернёт результат в исходный чат. Lead_seconds для обычного дайджеста

оставь штатным, если пользователь не задал особое требование к времени сбора.

Пример содержимого prompt (подставить реальные предпочтения и известный путь):

> Собери новостной дайджест по ИИ и потребительским технологиям за последние

> 24 часа относительно времени текущего запуска. Часовой пояс Europe/Moscow.

> Язык русский, кратко, до 7 важных событий. Источники: выбранная пользователем

> коллекция [конкретные URL]; дополнительные источники допускаются для проверки.

> Исключить криптовалюты. Для каждого пункта: что изменилось, почему важно,

> прямые ссылки, статус заявления и существенные неизвестные факты. Объединить

> перепечатки. При доступной истории этой подписки исключить уже включённые

> факты, но сохранить новые стадии и исправления. Если истории нет, обозначить

> невозможность сравнения. Назвать недоступные источники. При отсутствии свежих

> изменений сообщить это в пределах проверенного охвата. Не создавать новые задачи.

Не оставляй в настоящем prompt квадратные подстановки или ссылку «как обсуждали».

Путь к состоянию добавляй только после проверки доступа из планируемого контекста.

Если пользователь не задал конкретные источники, опиши темы и требования к поиску.

При запуске до времени доставки конец окна — время реальной проверки; не обещай

покрытие событий, произошедших после сбора.

Проверь результат create/update и покажи реальное расписание. При неоднозначном

исходе сначала list/status, а не повторный create. По запросу «не пришло» проверь

last_runs и отдельно различай выполнение, ошибку сбора и доставку.

Для отслеживания конкретного изменения («сообщи сразу, если изменилась цена»)

нужен отдельный monitoring workflow с baseline, а не регулярная новостная сводка.

Интерактивная сводка

Создавай страницу, если пользователь её попросил или подборка требует удобной

навигации по многим темам/событиям. Короткий дайджест доставляй прямо в чат.

При отсутствии sandbox сохрани полезную текстовую сводку со ссылками.

Страница

Штатному coder передай проверенные данные, период/timezone/checked_at, выбранные

темы, статусы и ограничения покрытия. Самостоятельный HTML должен содержать:

  • Мобильную читаемую ленту событий и фильтры по темам/источникам/статусу.
  • Поиск по тексту, раскрываемые детали и исходные ссылки у каждого события.
  • Хронологию по подтверждённой дате события; неизвестную дату выделить отдельно.
  • «Новое / обновление истории / контекст» только при наличии оснований.
  • Сохранённые пользователем пункты и отметки прочитанного с localStorage.
  • Экспорт выбранных пунктов и данных в JSON; печать без элементов управления.

Один набор данных должен определять карточки, фильтры, хронологию и экспорт.

Показывай число событий, а не число статей: несколько источников одного события

раскрываются внутри карточки. Не рисуй график «важности» из выдуманных чисел.

Покажи недоступные источники и время сбора рядом с границами периода.

Данные источников вставляй как текст, не как исполняемый HTML. Импорт JSON проверяет

форму данных и допустимые http/https-ссылки. Скрипты/iframe удалённых страниц не

встраивай. Внутренняя локальная отметка прочитанного не синхронизируется с источником

или krche. Не обещай live-обновление, совместный доступ или AI-ответы в офлайн HTML.

Для новых данных/разбора свободного вопроса пользователь возвращается к агенту.

Проверка и доставка

Через доступный штатный browser-use открой файл, проверь мобильную ширину,

фильтры/поиск, раскрытие источников, сохранение после reload и экспорт.

Выборочно проверь существенные исходные ссылки; недоступные отмечай, а не удаляй

сам факт отказа. Получи скриншоты страницы и отправь их с HTML через send_file

по фактическим путям. Обозначь, если визуальная проверка недоступна.

Используй существующий хостинг только при его доступности и поручении пользователя.

Доставленный файл не является опубликованной или постоянно обновляемой лентой.

Источники и интеграции

Порядок выбора

  • Явно выбранные пользователем и доступные персональные источники/tools.
  • Нативные web search/extract для поиска, полного текста и независимой проверки.
  • Прямые публичные RSS/Atom/JSON feeds при доступном пользовательском sandbox.
  • Подтверждённый MCP, если он даёт нужный доступ, которого предыдущие пути не дают.

Не устанавливай отдельный RSS-reader, embeddings, базу статей или scheduler ради

обычной подборки. Для большого корпуса используй source-research. Закрытый канал,

paywall или отсутствие доступа к истории нельзя заменить обещанием полного покрытия.

Telegram-публикации читай только через реально доступную ссылку/подключение; не

обещай доступ ко всем сообщениям канала и не создавай пользовательский аккаунт.

Публичные ленты

Feed — способ обнаружить материалы, а не доказательство каждого утверждения.

Сначала получи записи, затем открывай только отобранные исходные статьи. Feed может

содержать только последние записи; отсутствие в нём не доказывает отсутствие

публикации за весь интервал. Сохраняй GUID/Atom ID, исходные ссылки и даты как данные,

не превращай дату feed update в дату события.

При первом нужном вызове проверь наличие парсера в постоянной проектной среде

sandbox. Для обычного RSS/Atom достаточно Python stdlib HTTP/XML; XML нельзя

разбирать регулярными выражениями. Используй нативные ограничения сетевого доступа,

таймаут, ограниченный размер ответа и проверку конечного адреса после redirects;

не отключай их ради ленты. Если форматы сложнее, выбери проверенную закреплённую

версию feedparser в проектном venv, установи её только там и проверь один выбранный

feed. Переиспользуй рабочую установку; не скачивай весь архив издателя.

Официальная документация: Python XML,

feedparser.

MCP

Отдельный feed MCP не требуется: stdlib XML/проверенный feedparser закрывают

публичные ленты в существующем sandbox. feed-mcp (37 звёзд на 2026-10-09) исключён

из default установки/вызовов. Для нового стороннего MCP требуется конкретный repo

>1000, лицензия, pin, источник, изоляция состояния и реальный read-only smoke.

Порог относится только к MCP, не библиотеке feedparser. Не снимай no_mcp-гейты

и не создавай второй scheduler/backend для RSS. При ошибке продолжай native web.

krche — будущая интеграция

Сейчас пакет не подключает krche. Не вызывай придуманные endpoints или будущие

тулы и не запрашивай служебные ключи у пользователя. После реализации штатной

интеграции проверь фактически выданные схемы news_feed/news_sources/news_interests

или их актуальные аналоги, доступность в интерактивном и cron-контекстах и привязку

к тому же человеку. Shared/test feed не объявляй личной коллекцией.

Ленту используй для отбора, полный материал — для проверки, исходный URL — для

ссылки. Сохраняй krche entry/story ID для продолжения разговора и сравнения выпусков.

Пересказ внутри krche не является независимым источником или подтверждением.

При обрезанной статье/ошибке ответа обозначай ограничение. Истории и группы дублей

krche — подсказки для редакционного объединения, их конкретные утверждения проверь.

Чтение ленты не разрешает добавление/удаление подписок, изменение интересов,

mark-as-read или сброс. Такие действия выполняй по соответствующему поручению

через нативную интеграцию и её правила подтверждения. Для обычного дайджеста они

не нужны. Скилл и формат результата остаются теми же при смене поставщика данных.

Среда, проверка и доставка

Читай для файлов, интерактивного HTML или исполнения задачи; уже прочитанную

общую инструкцию в текущей беседе повторно не загружай. Предметные критерии

проверки определяет выбранный навык.

Объём работы и среда

Простой ответ, короткий черновик, обычный рецепт или расчёт выполняй в чате.

Создавай HTML для сложного плана, сравнения, динамики или по запросу; один пункт

не требует страницы. Файл в заказанном формате остаётся обязательным.

Переиспользуй native web/vision/STT, coder/исполнение, browser и sender.

Проверяй реально выданные инструменты и их схемы. Не создавай второй scheduler,

browser runtime или sender. API/MCP используй только при доступном подключении;

допуск стороннего MCP требует >1000 GitHub-звёзд, официальные API разрешены напрямую.

Файлы и зависимости находятся в личной sandbox, не в gateway. Skills prepare

возвращает путь пакета; пути вложений получай через штатный импорт/список файлов.

Путь для vision и байты для обработки могут требовать разных инструментов.

Установи только зависимости нужной ветки в проектную среду при первом вызове;

переиспользуй рабочие версии, сохраняй lockfile и оригиналы. Личные устройства

и аккаунты не становятся доступными из облачной sandbox автоматически.

Проверка

Проверь сохранённый итоговый файл, независимые расчёты и необходимые предметные

условия. HTML проверяй headless через доступный browser-use/Chromium: реальные

действия, связанные показатели, empty/error states, desktop/mobile и console.

Сохрани настоящие скриншоты. Снимок другого представления не доказывает качество

DOCX/PDF/PPTX, статичный кадр — плавность анимации. Детали рендера задаёт форматная ветка.

Долгую работу веди штатно с реальным job/operation handle. Проверяй существующую

операцию, не запускай дубль при busy/pending. Сохраняй exit code и связывай проверку

с актуальной версией файла; отменённая проверка остаётся непроверенной.

Инструкции при передаче исполнителю

В задании coder/другому исполнителю укажи точный skill_ref из успешного чтения

и пути references для текущего этапа. Исполнитель должен прочитать SKILL.md и эти

references перед предметной работой: по закреплённой версии через native read

или из пакета, подготовленного по тому же skill_ref. Укажи результат, входные

материалы и критерии проверки. Не считай одно название навыка доказательством

прочитанных инструкций; при новом этапе загружай только нужную ветку.

Состояние и передача

Страница без backend показывает snapshot. Не обещай live chat, общую историю или

автоматическое сохранение: дай экспорт и проверяемый путь импорта в личный workspace,

если они нужны. Не помещай секреты в HTML/архив и не публикуй личные данные по умолчанию.

Передай заказанный файл штатным sender по подтверждённому пути. Скриншоты

отправляй по запросу или когда они помогают объяснить результат; сохранение

скриншотов для QA само по себе не требует их доставки.

Локальный путь или localhost не являются пользовательской ссылкой. Login/captcha

передавай через штатный handoff. Неизвестный исход внешней операции сначала проверь

по фактическому состоянию. Создание файла не разрешает покупку, отправку или запись.

Календарь, порученные напоминания и доставка остаются native. Наблюдение за

изменениями передавай change-monitoring с объектом, источником, условием и частотой;

он владеет baseline/сравнением, штатный cron — расписанием и доставкой.
