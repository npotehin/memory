Работа с содержанием

Сохрани оригиналы. Установи назначение, читателя, формат и шаблон из запроса;

уточняй только пробелы, меняющие результат. Сохраняй стиль и неподлежащие изменению

части существующего документа. Для нового DOCX используй при необходимости

assets/document-style.json.

Проверяй имена, суммы, даты, решения и реквизиты по материалам. Не превращай

предложение в принятое решение. Голосовые обрабатывай штатным STT; черновик письма

или протокол сам по себе не поручает отправку, создание задач или событий.

MarkItDown извлекает содержимое, но не сохраняет исходную вёрстку для редактирования.

У PDF сохраняй реальные номера страниц, отмечай неполное извлечение и OCR-неуверенность.

Для таблиц с важными ячейками используй форматный reader; не восстанавливай номера

страниц или координаты ячеек из предположений о Markdown.

Вопросы по большому корпусу, суммаризацию книг и поиск с проверяемыми цитатами

передавай source-research с исходниками и целью. Обычное чтение одного документа

не требует создания корпуса. XLSX/CSV выполняет spreadsheets, статистику и

аналитические дашборды — data-analysis, презентации — presentations.

Проверка и доставка

Повторно открой итоговый файл, сверь содержание, структуру и существенные значения.

Отрендери все новые/изменённые страницы и проверь таблицы, переносы, поля и шрифты.

Для полей/оглавления нужен совместимый Office renderer с обновлением полей;

при его отсутствии обозначь непроверенную часть. После экспорта проверь PDF отдельно.

Сохраняй исходник и проверяй именно последнюю редакцию. Выдай заказанный файл

штатной доставкой; дополнительный HTML создавай по запросу или когда он помогает задаче.

DOCX: технические решения

Обычные операции

python-docx позволяет создавать paragraphs, styles, таблицы, изображения, sections и headers/footers. Для новых документов задай Normal и Heading styles и размеры/поля страницы до наполнения. Размеры указывай через библиотечные единицы, например Cm/Pt, а не случайные EMU.

Для точечной правки сохраняй runs с разными стилями; совпадение текста может пересекать несколько runs. Сначала выясни структуру и выбери поддерживающий её метод. Hyperlinks, content controls, footnotes, tracked changes и некоторые embedded objects требуют отдельной проверки возможностей выбранного инструмента.

Не присваивай paragraph.text вслепую для локальной замены: это уничтожает runs

и встроенные элементы. Для сложной сохранности предпочитай доступную Office

автоматизацию. Кириллица требует совместимого шрифта; заголовок должен оставаться

с последующим текстом. Не имитируй таблицы пробелами и page breaks пустыми абзацами.

Списки, таблицы и страницы

Используй существующие numbering definitions для правки шаблона. Для нового документа применяй соответствующие paragraph styles/numbering; отступы и табуляция должны быть согласованы. Таблицы не должны выходить за полезную ширину страницы; повтор заголовков проверяй в рендере. Для крупных таблиц горизонтальная секция или приложение лучше сверхмелкого шрифта.

Колонтитулы и page numbers зависят от sections и link-to-previous. Проверяй первую страницу, переходы sections и последнюю страницу. Не обещай конкретное число страниц до рендера: шрифты и layout engine меняют пагинацию.

Render и PDF

LibreOffice/Word работают с копией и отдельным output directory. Для headless LibreOffice используй изолированный profile, чтобы не конфликтовать с другим процессом. Пересоздай preview после последней правки. PDF/скриншоты подтверждают внешний вид; повторное чтение DOCX подтверждает содержание. Нужны оба вида проверки, если задача включает верстку.

Официальная документация: https://python-docx.readthedocs.io/en/latest/user/quickstart.html

PDF: извлечение, OCR и создание

Извлечение по страницам

В PyMuPDF используй page.get_text("text", sort=True) как начальную точку; порядок чтения всё равно проверяй на сложной верстке. В pypdf используй page.extract_text() и сохраняй page index. PDF без текста требует OCR. Для таблиц pdfplumber позволяет пробовать линии/координаты; геометрическая таблица не гарантирует правильную семантику.

Для передачи notebook составь UTF-8 JSON с locator и text для каждой страницы. Пустые страницы сохрани в отчёте извлечения, но не представляй как успешный OCR. Длинные таблицы можно извлекать отдельно в CSV с привязкой к страницам.

OCR

Проверь установленные языки Tesseract; для русского обычно нужен rus, для смешанного текста — rus+eng. OCRmyPDF добавляет text layer и полезен для поискового PDF, но не обязательно исправляет reading order. Не заменяй исходник. На числах, датах, таблицах и именах сделай выборочную сверку с увеличенными изображениями, особенно если они используются в решении.

Создание

В ReportLab предпочитай flow-based Platypus для многостраничных документов. Зарегистрируй доступный Unicode TTF, настрой styles и повтор заголовков таблиц. В HTML-печати явно задай A4/Letter, page margins, print styles, break-inside/break-before и скрытие интерфейса. Страницы и таблицы должны проверяться после финальной конвертации.

Для страниц pypdf/PyMuPDF используют индексы с нуля: пользовательские «страницы 2–5» означают индексы 1–4. После склейки проверь оглавление, ссылки, ориентацию и формы, если требуется их сохранение.

Официальные руководства: https://pymupdf.readthedocs.io/en/latest/recipes-text.html, https://pypdf.readthedocs.io/en/stable/ и https://ocrmypdf.readthedocs.io/en/latest/

Работа с PDF

Работай в пользовательской sandbox, сохраняя исходный файл. Проверь доступные инструменты: pypdf/PyMuPDF для чтения/страниц, pdfplumber для таблиц, Tesseract/OCRmyPDF для сканов, ReportLab или HTML-печать для создания, Poppler/браузер для рендера. Не предполагай, что все они установлены.

Режим

  • Чтение: осмотри metadata/page count, извлеки текст со страницами; сложные колонки/таблицы проверяй по рендеру.
  • Скан: отсутствие text layer не означает пустой документ. Примени доступный OCR с нужным языком и проверь числа, имена и таблицы по изображению.
  • Извлечение таблиц: сначала установи реальные заголовки и структуру, затем экспортируй CSV/XLSX. Не считай строки с переносом отдельными записями.
  • Создание: выбери понятную иерархию, шрифты с кириллицей, размеры страницы, поля, колонтитулы и правила переноса таблиц.
  • Правка/страницы: сохрани исходник, порядок страниц и важные bookmarks/формы/annotations, если они входят в задачу. Для redaction используй настоящее удаление содержимого, а не белый прямоугольник.

Технические приёмы: references/pdf-workflows.md.

Проверка

После сохранения открой файл заново, проверь page count и извлечение ключевого текста. Отрендери и просмотри все новые/изменённые страницы; для созданного с нуля PDF — каждую страницу. Проверь обрезки, таблицы, непреднамеренные пустые страницы, пропавшие glyphs и переполнение колонтитулов.

После удаления чувствительного текста проверь не только изображение, но извлечение текста, annotations и вложения. Не называй документ обезличенным по одному визуальному просмотру.

Большие источники

Для суммаризации передай source-research извлечённые страницы в JSON [{"locator":"стр. 1","text":"..."}]. Сохрани оригинальный PDF и отметку OCR, чтобы цитаты можно было проверить. Не помещай многосотстраничный текст целиком в основной диалог.

Передай итоговый PDF и, если создан отчёт, редактируемый источник по запросу. Укажи неполные/OCR-неуверенные участки, если они влияют на вывод.

Письма, протоколы, отчёты и версии

Протокол встречи

Работай с доступной транскрипцией/заметками; исходное аудио сначала проходит

нативный STT workflow Hermes. Входящие голосовые могут уже содержать транскрипцию:

переиспользуй её, сохрани привязку к сообщению/записи и доступные timestamps.

Для аудиофайла используй доступное штатное распознавание; MarkItDown/audio extras

или собственный STT сервер ради протокола не нужны. Не приписывай реплики

участникам, если speaker labels не подтверждены. Ошибки распознавания имён,

сумм и дат отметь и уточни перед включением в решения.

Разделяй обсуждение, предложение и принятое решение.

Для задачи фиксируй действие, явно названного ответственного, срок и evidence.

Не назначай человека или дату из предположения; пометь «не указан» и уточни

существенный пробел. Противоречащие версии решения показывай раздельно.

Файл может содержать краткое резюме, решения, задачи и открытые вопросы.

Создание todo/calendar/cron — отдельное поручение через нативные инструменты.

Письмо и заявление

Определи адресата, цель, желаемое действие, факты и тон из контекста. Реквизиты,

даты, суммы и номера берутся из пользователя/источника; пробелы видны в черновике.

Для заявления предпочитай приложенный действующий шаблон, сохраняй его поля.

Требования не определяй по старому образцу; при запросе на них нужна отдельная

актуальная проверка. Черновик доступен в чате; файл — по задаче.

Отправлять только по поручению, с подтверждёнными адресатами и фактическим outcome.

Письмо подрядчику должно содержать конкретное требуемое действие, основания из

переписки, согласованные условия и срок, если он известен. При смене тона не

меняй обязательства. Заполненное заявление проверь по каждому полю шаблона;

неизвестные обязательные поля выведи списком, не заполняй примерными данными.

Отчёт и предложение

Выдели цель, выводы, факты/расчёты, условия и следующие действия. Условия,

обещания и цены не добавляются из шаблонного примера. Таблицы со значимыми

расчётами передай spreadsheet workflow, итоговые сведения сверяй с источником.

Оформление использует единый стиль документа; проверяй страницы после рендера.

Для коммерческого предложения собери задачу клиента, объём работ, результат,

этапы/сроки, цену/валюту/налоги и условия, только если они заданы. Сделай читаемые

заголовки и таблицу условий, проверь итоговые суммы. По запросу выдай редактируемый

DOCX и отдельный PDF, сверив содержание и вёрстку обоих артефактов.

Редактура и сравнение версий

Отделяй орфографию/стиль от смыслового изменения. Проверь реквизиты, даты,

суммы, ссылки на пункты, повторение и противоречия. Сравнивай разделы и таблицы,

а не только порядок абзацев: перемещение не всегда удаление/новый текст.

В выдаче указывай исходную и новую формулировки, location и последствие изменения.

Полное сравнение требует пройти все разделы обеих версий и сопоставить структуру,

включая добавленные/удалённые пункты, таблицы, обязательства, даты и суммы.

Поиск по top-K не является исчерпывающим diff. Для вопроса по отдельной теме

В source-research grounded search/ask с двумя --source-id автоматически балансирует источники;

--per-source включает этот режим для всех активных источников. Проверь coverage

и missing_source_ids: отсутствие evidence одного документа не доказывает

отсутствие условия. Полный change log готовь по последовательному сравнению

извлечённых разделов и сверяй существенные изменения с оригиналами.

Не обещай Word tracked changes, если выбранный renderer/library их не поддерживает;

передай отдельный change log или проверенную redline версию. Оригиналы сохраняй.

Для большого сравнения по запросу создай HTML с фильтром разделов, old/new и

переходами к evidence. Основной интерактив — уточнения и правки с пользователем.

Перед отправкой документа проверь орфографию, согласованность условий,

нумерацию/ссылки на пункты, реквизиты и актуальность подставленных данных.

После последней правки выполни render QA по docx-workflows/pdf-operations;

проверка текста не подтверждает отсутствие обрезанных таблиц или пустых страниц.

MarkItDown: first-use преобразование содержимого

Принят релиз 0.1.8, MIT,

Python >=3.10,<3.15. Это внешняя библиотека sandbox, не скопированный upstream

runtime. Наличие инструкции не означает установку в пользовательской среде.

Через coder проверь текущую project-local venv, Python и installed version.

Переиспользуй проверенную установку; отдельную .venv-documents создавай только

если среды ещё нет. Устанавливай нужные extras, например

python -m pip install 'markitdown[docx,pptx]==0.1.8' внутри этой среды.

Не устанавливай [all], Azure/audio extras или MCP ради одного DOCX. Не заменяй

системную среду и не добавляй глобальный сервер. При несовместимости pin проверь

поддерживаемый релиз и повтори smoke, не переходи молча на floating main.

Обычное чтение локального файла:


from markitdown import MarkItDown
result = MarkItDown(enable_plugins=False).convert_local("source.docx")
markdown = result.markdown

В source-research этот вызов использует bundled document_readers.py. Библиотека устанавливается

отдельно при первом вызове; portable broker tests подменяют converter fixture.

Smoke: небольшой русский DOCX с heading/table → конверсия → проверить фактические

значения и структуру. Для нужного другого формата выполнить отдельный smoke.

Не печатай содержимое конфиденциального документа в диагностику целиком.

MarkItDown преобразует содержимое для анализа; сохранение исходного DOCX layout,

правки, render QA и печатный PDF используют форматные инструменты documents.

convert_stream принимает BinaryIO, но результат — готовая строка Markdown;

не считай это доказанной потоковой постраничной обработкой.

Public MarkItDown() создаёт Magika classifier; это небольшая локальная neural

модель определения формата, не LLM. Даже базовый пакет содержит Magika dependency.

При строгом требовании «никаких локальных моделей» не объявляй обычный вызов

совместимым: нужен отдельно проверенный прямой converter/другой reader.

Не патчи библиотеку или не ставь её без обязательных зависимостей ради обхода.

Для grounded цитат обычный Markdown не гарантирует страницы. PDF извлекай с

page locators через pypdf; generic DOCX-конверсия — converted_markdown

chars/lines, а heading/paragraph/table требуют отдельного проверенного адаптера; EPUB/FB2 — главы,

spine/anchors/paragraphs. Неподтверждённые страницы не добавляй.

Скан без текста требует отдельного OCR, не считается пустым источником.

Среда, проверка и доставка

Читай для файлов, интерактивного HTML или исполнения задачи; уже прочитанную

общую инструкцию в текущей беседе повторно не загружай. Предметные критерии

проверки определяет выбранный навык.

Объём работы и среда

Простой ответ, короткий черновик, обычный рецепт или расчёт выполняй в чате.

Создавай HTML для сложного плана, сравнения, динамики или по запросу; один пункт

не требует страницы. Файл в заказанном формате остаётся обязательным.

Переиспользуй native web/vision/STT, coder/исполнение, browser и sender.

Проверяй реально выданные инструменты и их схемы. Не создавай второй scheduler,

browser runtime или sender. API/MCP используй только при доступном подключении;

допуск стороннего MCP требует >1000 GitHub-звёзд, официальные API разрешены напрямую.

Файлы и зависимости находятся в личной sandbox, не в gateway. Skills prepare

возвращает путь пакета; пути вложений получай через штатный импорт/список файлов.

Путь для vision и байты для обработки могут требовать разных инструментов.

Установи только зависимости нужной ветки в проектную среду при первом вызове;

переиспользуй рабочие версии, сохраняй lockfile и оригиналы. Личные устройства

и аккаунты не становятся доступными из облачной sandbox автоматически.

Проверка

Проверь сохранённый итоговый файл, независимые расчёты и необходимые предметные

условия. HTML проверяй headless через доступный browser-use/Chromium: реальные

действия, связанные показатели, empty/error states, desktop/mobile и console.

Сохрани настоящие скриншоты. Снимок другого представления не доказывает качество

DOCX/PDF/PPTX, статичный кадр — плавность анимации. Детали рендера задаёт форматная ветка.

Долгую работу веди штатно с реальным job/operation handle. Проверяй существующую

операцию, не запускай дубль при busy/pending. Сохраняй exit code и связывай проверку

с актуальной версией файла; отменённая проверка остаётся непроверенной.

Инструкции при передаче исполнителю

В задании coder/другому исполнителю укажи точный skill_ref из успешного чтения

и пути references для текущего этапа. Исполнитель должен прочитать SKILL.md и эти

references перед предметной работой: по закреплённой версии через native read

или из пакета, подготовленного по тому же skill_ref. Укажи результат, входные

материалы и критерии проверки. Не считай одно название навыка доказательством

прочитанных инструкций; при новом этапе загружай только нужную ветку.

Состояние и передача

Страница без backend показывает snapshot. Не обещай live chat, общую историю или

автоматическое сохранение: дай экспорт и проверяемый путь импорта в личный workspace,

если они нужны. Не помещай секреты в HTML/архив и не публикуй личные данные по умолчанию.

Передай заказанный файл штатным sender по подтверждённому пути. Скриншоты

отправляй по запросу или когда они помогают объяснить результат; сохранение

скриншотов для QA само по себе не требует их доставки.

Локальный путь или localhost не являются пользовательской ссылкой. Login/captcha

передавай через штатный handoff. Неизвестный исход внешней операции сначала проверь

по фактическому состоянию. Создание файла не разрешает покупку, отправку или запись.

Календарь, порученные напоминания и доставка остаются native. Наблюдение за

изменениями передавай change-monitoring с объектом, источником, условием и частотой;

он владеет baseline/сравнением, штатный cron — расписанием и доставкой.
