# Доставка и публикация мобильного отчёта

Файл отдаётся вложением в чат — в мессенджере он открывается встроенным
просмотром, и вёрстка должна выглядеть там же, а не только в полноценном
браузере. Постоянная ссылка требует публикации, а это отдельный запрос;
не обещать адрес раньше времени.

## Постоянная ссылка: что важно сказать сразу

Публикация через GitHub Pages или Cloudflare Pages — отдельная задача, и до
разговора о ней стоит честно назвать два ограничения, иначе обещание
придётся забирать назад:

- у облачной машины нет входящего адреса, поэтому «открыть файл по ссылке с
  моей машины» нельзя — нужен внешний хостинг;
- Cloudflare Pages на бесплатном тарифе **не делает сайт приватным**:
  опубликованное доступно по адресу любому, кто его знает. Для закрытых
  документов нужен Cloudflare Access (вход по почте) либо хранение ленты
  внутри приватного репозитория без публикации. GitHub Pages на бесплатном
  тарифе — тоже только публичный сайт.

## Лента обновлений вместо ссылок в чате

Рабочая схема, когда файлов много и человек читает с планшета: в корне
репозитория лежит `index.html` — лента «что добавилось и когда», сгруппированная
по папкам (Отчёты / Стили / Проекты) и с датами из `git log`. Человек обновляет
одну страницу и видит новое, вместо того чтобы искать ссылку в переписке.

Лента не собирается сама: нужен скрипт (`build_index.py`, даты берутся из
`git log --name-only --pretty=format:%cd --date=short`, при отсутствии записи —
`mtime`). Собирать её перед пушем.

## Сначала проверить, что Actions вообще запускаются

Прежде чем отлаживать workflow, посмотреть, стартовал ли job хоть раз.
Признак «не про код»: все прогоны падают примерно за секунду, у job нет ни
одного выполненного шага, а логи отдаются как `BlobNotFound`.

Тогда причина не в workflow. Притягивается она аннотацией чек-рана:
`GET /repos/{owner}/{repo}/check-runs/{job_id}/annotations` — запрос с
заголовком авторизации, токен подставляется из окружения, а сам токен в
команду не вписывают. Готовая формулировка, которая встречалась:

> The job was not started because recent account payments have failed or
> your spending limit needs to be increased.

Это значит, что минуты Actions у аккаунта кончились или не привязана оплата, и
**никакой workflow не запустится**. Для приватного репозитория минуты платные:
пара отладочных прогонов расходует бесплатный остаток целиком.

В этом случае Actions не чинить — уходить на Git-интеграцию Cloudflare
(следующий раздел) и удалять `.github/workflows/*`: мёртвый workflow только
создаёт впечатление, что деплой настроен.

## Git-интеграция Cloudflare Pages — предпочтительный путь

Если пользователь готов подключить репозиторий в панели Cloudflare, это
лучше Actions: минуты GitHub не тратятся, workflow не нужен, деплой переживает
любые проблемы с биллингом GitHub.

Параметры для статики, которая уже лежит в репозитории собранной:

```
Framework preset     None
Build command        пусто
Build output dir     .
Root directory       пусто
Production branch    main
```

Дать интеграции доступ **только к нужному репозиторию**, не ко всем. Если
репозитория нет в списке — GitHub → Settings → Applications → Cloudflare Pages
→ Configure.

Проверить результат можно без панели, по API проекта: `source.type` должен
стать `github`, в `source.config` появиться `repo_name` и `production_branch`,
а `latest_deployment.latest_stage.status` — `success`.

У пользователя может быть несколько аккаунтов Cloudflare; список аккаунтов
может вернуться пустым даже при живом токене. Тогда Account ID брать из
прошлой переписки, а не из этого ответа, и проверять проект по нему напрямую.

## Hours на новом репозитории

Новый репозиторий Pages не знает: проект надо один раз создать в панели и
привязать к нему репозиторий. После этого каждый пуш пересобирает сайт сам.
Имя проекта задаёт адрес: `имя-xxxx.pages.dev`, четыре символа добавляет
Cloudflare. Имя репозитория ни на что не влияет. Переименование проекта
меняет адрес, старый перестаёт открываться — выбирать сразу.

## Диагностика красного деплоя

Логи job через API **не читаются**: запрос логов прогона отдаёт
`BlobNotFound` в XML. Поэтому причину искать так:

1. Список прогонов: `/actions/runs?per_page=1` → `status`, `conclusion`.
2. Шаги: `/actions/runs/{run_id}/jobs` → у каждого job `conclusion` по шагам;
   это уже показывает, на каком шаге упало, без лога.
3. Аннотации чек-рана — короткий текст причины, если шаги не стартовали.
4. Прогнать те же команды локально на облачной машине — если локально чисто,
   разница в окружении workflow (права, ветка, версия actions).
5. Отдельно проверить токены прямыми запросами к API GitHub и Cloudflare:
   если оба отвечают, проблема в workflow, а не в доступе.

Пока workflow разбирается, публикацию не блокировать: собрать страницу и
залить её напрямую с машины, а автоматизацию починить следом. Не отправлять
пользователя смотреть логи в интерфейс GitHub, если он просил вести рутину
через консьержа.

## Про доступ и входы: проверенный порядок

Пользователь может создать отдельные сервисные аккаунты под консьержа
(имя, GitHub, Cloudflare, почта) — это предпочтительнее доступа к личным.
Дальше важны три вещи, на которых уже спотыкались.

**Вход — только через экран (`desktop` handoff).** Пароли в чат не
принимаются. Пользователь открывает `screen_link` со своего устройства и
входит сам; коды подтверждения читает в соседней вкладке там же, на экране.
Сессия остаётся в профиле браузера облачной машины и переживает сон.

**Проверять, на какой машине вход.** Пользователь может залогиниться в
своём браузере (или в виртуалке) и искренне считать, что вошёл «на облаке».
Перед работой сверять факт: `desktop(screen_action='status')` показывает
текущий `page.url`, скриншот — аватар или форму входа. Вход на домашней
машине не переносится в облачную.

**Профиль браузера может не сохранять входы.** Перед обещанием «всё
останется после перезапуска» проверить размер и содержимое профиля: пустой
профиль (десятки килобайт, внутри только отчёты о сбоях) значит, что сессии
живут в памяти и после сна пропадут. Тогда честно сказать: файлы и токены
останутся, входы в панели придётся повторить. Токены, лежащие в git-remote и
в секретах репозитория, от состояния браузера не зависят.

**Буфер обмена не общий.** Токен, скопированный в браузере пользователя на
его устройстве, на облачной машине недоступен: `xclip`/`xsel` там могут
отсутствовать, а `xdotool` вставляет только то, что уже в буфере дисплея.
Попытки протащить токен через терминал на экране (`cat > файл`,
`Ctrl+Shift+V`, `xdotool type`) на практике не срабатывают и съедают время.
Не изобретать обходной путь: если вход через экран не завершён, честно
попросить пользователя создать **fine-grained PAT на один репозиторий,
право Contents: read/write, срок 7 дней** (создаётся в его собственном
браузере за минуту), либо залить файлы через веб-интерфейс руками.

**Гигиена токена.** Если токен всё-таки прошёл через переписку — сразу после
заливки удалить его из конфигурации машины и напомнить, что отозвать можно в
`Settings → Developer settings → Personal access tokens`. Никогда не хранить
токен в репозитории, в скриптах или в ленте.

## Что проверить после публикации

- лента открывается по адресу и перечисляет свежие файлы с датами;
- ссылки из ленты ведут на существующие файлы (относительные пути, не абсолютные);
- если включён Access — без входа страница не открывается, с входом — открывается;
- деплой зелёный, и в истории деплоев Cloudflare видно новую ревизию.

## Когда проверка из облака врёт

`curl` с облачной машины может получить `000` и `TLS unexpected eof` на
живом внешне сайте: сеть ходит через общий исходящий шлюз, и TLS до
определённых хостов рвётся. Это не значит, что сайт лежит. Различать так:

- IPv4 (`curl -4`) может ответить `200`, пока общий запрос падает;
- адрес вида `<hash>.<project>.pages.dev` — адрес конкретного деплоя, он
  отвечает независимо от основного домена;
- окончательная проверка — `desktop(action='browse')` с задачей «открыть
  страницу и сказать заголовок и есть ли ошибка». Браузер на экране ходит
  другим путём и видит то, что видит человек.

Вывод делать по браузеру, а не по коду ответа `curl`. И не рассказывать
пользователю про шлюз, если он просто спросил, работает ли сайт.
