# Наблюдения и уведомления

Для работы с файлами, HTML и sandbox читай общую инструкцию
[references/runtime-and-delivery.md](references/runtime-and-delivery.md).

Закрой цикл «выбрать объект → проверить источник → зафиксировать исходное состояние
→ сравнивать → уведомлять → изменить/остановить». Нативный cron владеет расписанием
и доставкой; sandbox пользователя — скриптом и состоянием. Browser-use помогает
настроить извлечение и проверить его, Scrapling — повторять извлечение без модели.
Отдельный changedetection.io, браузер, scheduler или MCP не требуются.

## Выбор ветки и этапа

Выбери ветки по требуемому результату. Прочитай указанные инструкции перед
соответствующим этапом; осмотр вложений и уточнения могут предшествовать ему.
В составной задаче загружай ветки по мере перехода к этапам, а не весь пакет.

## Контракт наблюдения

Возьми из запроса объект, источник, сравниваемое поле, условие, частоту и срок.
Сохрани идентичность: SKU/вариант/продавец/регион, дата поездки или спектакля,
поисковые фильтры вакансий либо конкретный раздел/папка. Не сравнивай разные
комплектации, валюты, тарифы, условия скидки или платёж в рассрочку с полной ценой.
Назови частоту проверки; обещание «сразу» ограничено ею и доступностью источника.
Не создавай постоянное задание из разового «проверь, изменилось ли».

Выбери условие: любое изменение, снижение/рост, строго ниже/выше порога,
достижение статуса, новые ID впервые или появление относительно предыдущей проверки.
Различай «ниже 30000» и «не дороже 30000»: helper поддерживает строгие пороги;
для включительной границы coder должен явно реализовать и проверить условие.
По умолчанию первый запуск создаёт baseline без объявления найденного новым.
Если пользователь просит сообщить о текущем выполнении условия, включи initial_notify.

## Подготовка и запуск

Пакет содержит исполняемый [scripts/watch.py](scripts/watch.py) и тесты. Подготовь его
через штатный `skills prepare`, затем используй подтверждённый путь. Helper — Python
3.10+, stdlib, без сетевых запросов, установки библиотек и собственной отправки.
Он принимает нормализованное наблюдение; получение данных выполняет отдельный
проверенный adapter в постоянном sandbox. Не называй наличие helper готовым live-монитором.

Для установки зависимостей и adapter используй штатный coder с полным контрактом.
Начни с API/RSS/HTTP, затем HTML через Scrapling; динамические страницы используют
существующий Chromium только через разрешённый lifecycle брокера.
Подробнее: [references/extraction.md](references/extraction.md).
Не подключай второй клиент к занятой вкладке browser-use и не закрывай чужой context.

Сохрани отдельный каталог каждого наблюдения внутри пользовательского workspace.
Нельзя брать baseline из общей PG, чужих сессий или директории gateway.
Создай config, выполни init, проверь успешное наблюдение и diagnostic result.
Схема, режимы, команды и состояния:
[references/state-and-runner.md](references/state-and-runner.md).
Не регистрируй change-only расписание до проверки постоянного состояния и доступа
к выбранному источнику из unattended-контекста; при отсутствии возможностей честно
дай разовую проверку/сводку без обещания непрерывного наблюдения.

Для детерминированной проверки используй cron `kind="script"`,
`script="computer:~/watch/<id>/check.py"`. Adapter берёт свежие данные и вызывает
helper; stdout содержит только уведомление, пустой stdout — тишина. Ошибка проверки
завершает запуск ненулевым кодом; не печатай «изменений нет» при отказе сайта.
Для смысла изменений допускается native agent job со самостоятельным брифом,
`skills=["change-monitoring"]` и доступом к тому же состоянию. Не вызывай LLM
для обычной проверки цены. Следуй нативному cron guidance и фактическим схемам.

## Валидация и эксплуатация

Перед расписанием проверь реальную страницу через browser-use, значение/единицу,
идентичность и условия; отправь полученный скриншот через send_file. Выполни повторный
запуск adapter без изменений: он должен молчать. На сохранённых fixture проверь
нужное изменение, повтор, отказ/неполный ответ, неверную валюту/объект, потерю
состояния и восстановление после перезапуска. Сценарии:
[references/validation.md](references/validation.md).
Fixture с выдуманной ценой не выдавай за реальный оффер.

Покажи, что наблюдаем, условие, расписание, источник, последний успешный результат
и статус настройки. Подтверждай создание задания фактическим ответом cron.
Изменение условий требует явного reset baseline/revision после сохранения истории;
пауза/остановка — обновление существующего задания, не создание дубля.

Наблюдение, подготовка сообщения и доставка — разные факты. Helper сохраняет событие,
но не подтверждает доставку; её проверяй через cron last_runs. При неизвестном исходе
не повторяй рассылку автономно. Повтор после подтверждённого отказа — через нативный
механизм; старое событие не объявляй новой проверкой. Если adapter сломался, сохраняй
последний хороший baseline; восстановление селектора не разрешает молча сменить товар.

## Совместное применение

Этот навык — единый владелец baseline, source adapter, сравнения и событий
изменения. Предметный навык передаёт объект/источник/условие/частоту, не создаёт
параллельный watcher. Штатный cron владеет только расписанием и доставкой.
shopping-research может передать точное предложение для слежения за ценой/наличием;
travel-leisure — выбранный билет/слот; career-assistant — запрос вакансий;
news-briefing — выбранные источники/истории. Только поручение на наблюдение создаёт
расписание. krche можно использовать после подтверждённой нативной интеграции,
а не через проектируемые endpoints. Наблюдение ничего не покупает и не бронирует.
Для большого списка по запросу создай HTML со статусами, графиком проверенных цен
и изменениями; управление cron через офлайн страницу не обещай.
