# Тренировки и прогресс с понятным основанием

Для работы с файлами, HTML и sandbox читай общую инструкцию
[references/runtime-and-delivery.md](references/runtime-and-delivery.md).

Закрой цикл: цель → исходные условия → выполнимая программа → запись факта →
разбор прогресса → изменение следующих занятий. Основной пользовательский
контекст — РФ, русский язык и привычные единицы; местоположение и часовой пояс
бери из контекста. Выбирай формат по задаче: короткий вопрос не требует dashboard.

## Повторная работа в персональном приложении

Если пользователь хочет постоянно вести план и факт упражнений, подходы, повторы и вес и доступен инструмент `apps`,
сначала проверь `apps(action="list")` и используй существующее приложение. Для нового
приложения передай в `apps build` предметный brief и `source_skills`: точный `skill_ref`
из успешного чтения этого навыка и нужные references текущего этапа. Builder получает
готовый шаблон `workout-log` через `hera-app templates` и адаптирует его под запрос.
Данные хранятся в базе приложения, общей для чата и экрана. Разовые ответы и файлы
продолжают использовать обычный workflow навыка. Draft/preview не означают публикацию;
публикуй только по явному поручению. Если `apps` недоступен, используй описанный ниже
файловый workflow и не обещай синхронизацию с приложением.

В составной задаче загружай ветки по мере перехода к этапам, а не весь пакет.

## Начало

Используй историю, имеющийся план и файлы. Для программы выясни цель, опыт и
текущую активность, доступное время/дни, оборудование, существенные ограничения
и известные рекомендации врача. Спрашивай ближайшее неизвестное, которое меняет
план; не собирай медицинскую анкету ради обычной прогулки.

Медицинские анализы, симптомы и историю передавай health-navigator с соблюдением
врачебных ограничений. Не назначай лечение, лекарства, дозировки добавок или восстановление травмы.
Новые боли, обморок, боль в груди или выраженное необычное затруднение дыхания —
причина остановить занятие и обратиться за медицинской помощью; исследование
не должно задерживать помощь. При беременности/после родов, болезнях, травмах
или врачебных ограничениях не переноси программу здоровых взрослых автоматически:
помоги уточнить допустимую активность с врачом, разъясни источники и следуй
подтверждённым ограничениям. Не объявляй человека медицински допущенным к спорту.

## Программа и упражнения

Прочитай [references/programs.md](references/programs.md). Для массового
пользователя поддерживай ходьбу/возвращение к активности, начинающий бег,
домашние занятия без оборудования/с резинками и силовые в зале. Зафиксируй
выбранную основу, кому она подходит, стартовую нагрузку, отдых, простую замену
упражнений и условия пересмотра. Авторскую адаптацию называй адаптацией,
не сертифицированной программой источника.

Каждое занятие должно быть исполнимо: разминка, упражнения/интервалы, подходы,
повторения или время, понятная интенсивность, отдых и завершение. Дай краткие
ориентиры выполнения и ссылки на проверенные объяснения/демонстрации. Каталог
упражнений не подтверждает пользу программы. Фото/видео можно разобрать через
native vision, но нельзя гарантировать по ним правильную технику и безопасность.

Прогрессируй по фактической переносимости и выполнению. Пропуск не создаёт
обязанность удвоить нагрузку; предлагай повтор этапа, перенос или более короткую
версию. Не применяй универсальный «+10% в неделю» или тренировки до отказа всем.

## PubMed и доказательность

Для вопроса «что эффективнее/правда ли/полезно ли» и существенного обоснования
нагрузки прочитай [references/evidence.md](references/evidence.md). Начинай с
релевантных рекомендаций, затем проверяй обзоры и исследования, меняющие решение.
PubMed — обязательный путь поиска в этой ветке, если доступен; при недоступности
отметь это и используй Europe PMC/официальные источники, не заявляй поиск PubMed.
Не делай новый большой literature search для каждой отметки выполненного занятия.

У вывода должны быть ссылки, участники/условия, сравнение, результат и ограничения.
Отделяй доказанный эффект от предположения и персональной применимости. Только
abstract — явно только abstract. PMID, название, размер эффекта и наличие полного
текста проверяй по записи, не придумывай. Общий механизм действия не доказывает
клинический эффект. Не превращай найденную статью в индивидуальное назначение.

Способы доступа и опциональные MCP —
[references/integrations.md](references/integrations.md). Native web/research — базовый путь. До нового подключения прочитай правило
допуска >1000 звёзд в integrations; рассмотренные MCP не проходят и исключены.
Официальные NCBI/Europe PMC/wger API разрешены без GitHub-фильтра библиотек.
Для структурированных данных используй stdlib helper по
[references/official-api.md](references/official-api.md); новый MCP не требуется.
Публичный поиск получает обезличенный вопрос, не медицинский файл пользователя.

## Журнал, интерактив и проверка

Для повторной работы прочитай [references/progress.md](references/progress.md):
отдельно план и факт, время/единицы/источник, повторы импорта, версии программы.
Без доступной истории оцени только предоставленные данные. Не выдумывай прогресс,
потраченные калории, «биологический возраст» или вероятность достижения цели.

По запросу или для удобного ведения сложной программы/прогресса создай в sandbox мобильную
интерактивную страницу по [references/interactive.md](references/interactive.md):
что делать сегодня → неделя → запись занятия → реальные тренды → почему так.
Основной runtime — Python, небольшой JSON/CSV-журнал; XLSX/CSV переиспользуют
`spreadsheets`, аналитические графики — `data-analysis`, большой корпус статей — `source-research`. Отдельная БД/сервер,
локальная нейросеть, Node и фитнес-платформа не нужны для базового сценария.

Предметная проверка страницы: реальные взаимодействия, расчёты нагрузки,
план/факт и пустая история; общую browser QA/доставку выполняй по
runtime-and-delivery.
HTML snapshot не сохраняет изменения в Hermes автоматически: дай экспорт и
проверяемый путь импорта. Без sandbox помоги в чате и обозначь непроверенные файлы.

Напоминания/календарь создавай native cron/calendar по поручению пользователя;
не добавляй второй scheduler. Питание — `food-planning` с согласованными условиями,
инвентарь — `shopping-research`. Подключение часов, аккаунтов и записи в них
требуют реального персонального доступа; не обещай синхронизацию по названию бренда.

## Результат

Дай ближайшее понятное действие, программу/изменение, объяснение основания и
правило следующей проверки. В исследовательском ответе покажи, что известно и
что остаётся неопределённым. В отчёте — период, покрытие фактических данных,
сопоставимые метрики и причины изменения плана. Личные данные и страницы
доставляй в личный контекст пользователя, не публикуй общедоступно.
